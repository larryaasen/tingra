# Tingra Plug-ins: the next phase

*Plan of 2026-09-13, revised the same day for the ExtensionKit process model and the field comparison. **All sixteen decisions were approved by Larry on 2026-09-13**; Phase 0 (the spike) and Phase 1 (the app tier and Notes) were built the same day, recorded under their headings; the vocabulary moves into GLOSSARY.md, the enforcement bullets into CLAUDE.md, and the seam rows into the "Seams and plug-ins at a glance" tables in ARCHITECTURE.md as each phase lands. Spike findings are recorded under Phase 0 as they arrive.*

## Why this phase exists

The plug-in architecture is the feature that will ultimately drive adoption — the way VS Code's extension system, not its editor, is what made VS Code. That only happens if there are **many capable seams** a third party can tap, and if a plug-in author can build something the engine has never heard of (a notes pane, a rundown, a chat overlay, a tally-light bridge) without asking us to add a hook first.

Today every seam is a **host** seam: inputs, outputs, effects, media, and MCP tools, all defined in `TingraPlugInKit` and all headless — the CLI, the `serve` daemon, and the app activate the same plug-ins through the same `PlugInContext`. That is the right foundation and it does not change. What is missing is the other half: seams that only exist when there is a window. A notes plug-in needs a pane, a menu item, and somewhere to save its text; the host needs to know nothing about it, but the app does.

This document plans that second half, the process model it runs under, and the seams that follow it. The goal for the code is VS Code's *shape* — a small stable kernel, everything else a plug-in against named registries — applied to a broadcasting, recording, and livestreaming tool rather than an IDE.

## What the field teaches

Four plug-in systems bracket the design space Tingra sits in. OBS Studio is the closest product; VS Code is the model for breadth and composability; VST3 and Audio Units are the model for a real-time engine that hosts third-party code without dying.

| Dimension | OBS Studio | VS Code | VST3 / Audio Units | Tingra today (+ planned) |
|---|---|---|---|---|
| **Boundary** | C ABI (`libobs`), function-pointer tables in `obs_source_info` structs | JavaScript API over RPC; `package.json` declares everything static | COM-style C++ interfaces (VST3) or Objective-C/Swift protocols (AU) | Swift protocols in a Library Evolution module; Swift's stable ABI is the contract |
| **Process model** | In process. A plug-in crash is the most common OBS crash | Out of process by design. The extension host restarts; the window survives | VST3 in process by tradition; hosts increasingly bridge. AUv3 is always out of process as an app extension with a remote view | Host tier in process (the frame path). App tier out of process via ExtensionKit (this plan) |
| **Engine seams** | Sources, filters, transitions, encoders, outputs, services | None. VS Code has no engine; everything is UI and language tooling | Exactly one: an audio processor. Deep, not broad | Inputs, generators, media, effects, streaming, recording, tools. Planned: transitions, sinks, destination kinds |
| **UI model** | Data-driven property panes the host renders, plus raw Qt for docks and menus | Data-driven first (tree views, status bar, quick pick, settings); one escape hatch (webview in an isolated iframe) | The plug-in draws its own editor in a host-provided window; parameters are declared so a host can show a generic editor | Effects already declare parameters the app renders. Panes planned as remote SwiftUI views behind declared descriptors |
| **The universal verb** | obs-websocket requests and hotkeys | Commands: every action is a named command any extension, keybinding, or menu can invoke | Parameters and automation | MCP tools — and Decision 10 makes them the plug-in verb too |
| **Persistence** | `obs_data_t` JSON stored in the scene collection | `globalState`, `workspaceState`, settings | A state stream the host saves inside the project | Planned: project-scoped JSON in the document, app-scoped folder. The same split as all three |
| **Activation** | Everything loads at startup | Lazy, on declared activation events | Instantiated on demand | Everything activates at boot. Planned: activation on demand for the app tier |
| **Versioning** | `libobs` API version; rebuilds across majors are common | Additive API with an `engines.vscode` floor; proposed APIs gated | VST3 ABI stable for over a decade; VST2 to VST3 was the one break | SemVer, Library Evolution, CI diff against the last tag; the app tier adds a wire protocol, which is easier to keep compatible than an ABI |
| **Distribution and trust** | Signed and notarized bundles in a folder since OBS 28; no isolation | Marketplace; the extension host has full Node access, a known weakness | Folders the host scans; `auval` validates AUs; AUv3 ships in a container app, sandboxed | Host tier: signed bundles in a folder. App tier: ExtensionKit, sandboxed, enabled by the system |

**From VS Code** the parts worth copying are structural. Declarative descriptors mean the host renders menus and lists uniformly and can show them before the plug-in has even loaded. Commands as the universal verb are what make extensions composable, and Tingra's tools already play that role. Activation events let a host stop launching every plug-in at boot. Data-driven UI first, with an escape hatch second, is why VS Code stays coherent across thousands of extensions.

**From VST and AU** the strict split between the real-time processor and the editor is the same split as Tingra's host tier and app tier, and it is the reason the host tier stays in process. The host owning plug-in state inside the project file is what Tingra's project-scoped storage does. Declared parameters that the host can render generically already exist for effects (`EffectParameter`) and should extend to inputs and outputs. AUv3 is the precedent that matters most for the process model, and it gets its own section below.

**From OBS** breadth. Sources, filters, transitions, encoders, outputs, and services are the seams a broadcasting tool needs, and they map directly onto phase 4. Two things not to copy: everything in process is why plug-in crashes dominate its crash reports, and handing plug-ins the raw UI framework for docks leaked Qt into the plug-in API, so OBS cannot change its UI toolkit without breaking every dock.

**Where Tingra already stands apart:** it is the only one of the four with a typed, structured event bus as the observability contract, and the only one whose control surface was designed for agents first. Both carry over to plug-ins unchanged.

### The AUv3 precedent

Audio Units version 3 (iOS 9 and macOS 10.11, 2015) is the closest thing to a controlled experiment on the question this plan has to answer: can a real-time media host run UI-bearing third-party plug-ins out of process on Apple platforms, and what does it cost?

**What Apple did.** An AUv3 is an app extension (`.appex`) that ships inside a container app. The system launches it in its own sandboxed process — on macOS the hosting process is visible in Activity Monitor as `AUHostingServiceXPC` — and the host (Logic, GarageBand, AUM, Cubasis) never links the plug-in's code. Three things cross the process boundary:

- **Audio.** The host's real-time render thread calls the extension's render block through a shared-memory audio buffer and a real-time-safe signalling path Apple engineered for the purpose. It works, but it costs: per-render-cycle scheduling overhead and a higher CPU floor, and early AUv3 hosts glitched at small buffer sizes where in-process AUv2 did not. Apple's answer on macOS was an escape hatch, `AudioComponentInstantiationOptions.loadInProcess`, honoured only when the extension's Info.plist names an `AudioComponentBundle` framework the host may load directly. iOS never got the hatch; every AUv3 on iOS is out of process.
- **The UI.** The extension vends an `AUViewController`; the host embeds it as a remote view — the extension's process renders the pixels, the window server composites them into the host's window. Remote views had a rough first few years: sizing (`preferredContentSize`, later `supportedViewConfigurations`), keyboard focus, drag and drop, and hosts showing a blank until the extension activated were all real complaints, and all were fixed at the platform level over successive releases rather than by each host.
- **Parameters and state.** The extension declares an `AUParameterTree`; the host observes and automates parameters across the boundary, and saves the extension's `fullState` inside its own project file. The plug-in never touches the disk on its own behalf.

**What happened.** On iOS, AUv3 is the only Audio Unit form there is, and it carries a large commercial ecosystem — hundreds of instrument and effect apps hosted by GarageBand, AUM, Cubasis, and Logic Pro for iPad, which is AUv3-only. On macOS, AUv3 coexists with AUv2 and VST3; many developers still ship v2 or VST3 first, for two reasons that matter here: the audio-path performance tax and the container-app distribution requirement. The crash-isolation benefit is real and visible in daily use — a crashing AUv3 shows up as a failed plug-in slot Logic can reload, not a lost session.

**What it says for Tingra.** Four lessons, each mapped to a decision below.

1. **Keep the real-time path in process.** Apple's audio-over-XPC is the best-engineered version of the alternative, and it still needed an in-process escape hatch on macOS. Tingra's frame path is GPU-resident and tick-paced (CLOCK.md); the host tier stays in process, exactly as ARCHITECTURE.md already says for capture. *(Decision 1, unchanged.)*
2. **Out-of-process UI works at scale.** The remote-view mechanism AUv3 relies on is the same one ExtensionKit exposes to any host through `EXHostViewController`, a decade more mature than when AUv3 launched. A notes pane, a rundown, or a source list has none of the audio path's timing pressure. *(Decision 12.)*
3. **The host owns state; the plug-in declares parameters.** `fullState` in the project and `AUParameterTree` for the generic editor are, respectively, Tingra's project-scoped storage and its `EffectParameter` — the second generalised to every host-tier registration. *(Decisions 7 and 15.)*
4. **Distribution friction is real and accepted.** A container app the user installs and an extension the system enables is heavier than dropping a bundle in a folder. The AUv3 ecosystem shows developers accept it when the host is worth targeting, and `EXAppExtensionBrowserViewController` lets Tingra present the enablement step itself. *(Decision 13.)*

One more lesson is in what Apple *had* to add: the in-process hatch. Tingra's app-tier seam is therefore designed so that the descriptors and the wire protocol do not depend on the process boundary — if a first-party pane ever proves it needs in-process hosting, the seam allows it without a rewrite, and the spike below is what decides whether that day ever comes.

## The model: two tiers, one plug-in

**A plug-in has up to two halves, one per tier.** *(Decision 1)*

| Tier | Who hosts it | Process | Protocol package | What a plug-in registers | Examples |
|---|---|---|---|---|---|
| **Host tier** | the engine — CLI, `serve` daemon, app alike | in process (the frame path) | `TingraPlugInKit` (UI-free, unchanged) | inputs, generators, media providers, effects, streaming/recording services, MCP tools; later transitions, event sinks | camera capture, bars, HaishinKit output, `stream_start` |
| **App tier** | the app only — `apps/tingra-app` | out of process: an ExtensionKit extension the system launches and sandboxes | `TingraAppPlugInKit` (**new**; ExtensionKit + SwiftUI on the extension side) | panes, commands, settings panes, storage, windows, status items | a notes pane, a rundown, a stream-deck bridge's settings |

A plug-in is **host-only**, **app-only**, or **both**:

- **Host-only** — a `PlugIn` bundle, as every first-party plug-in is today. Loads everywhere; the external bundle loader of roadmap step 10 is its delivery path.
- **App-only** — an ExtensionKit extension against Tingra's extension point. The engine never sees it. A headless front end never loads it, because the host tier and the app tier are different artifacts, not different halves of one binary.
- **Both** — a host-tier bundle and an app-tier extension shipped together in one container app, under **one `PlugInID`** *(Decision 3)*: the same reverse-DNS identifier is the bundle's plug-in id, the extension's declared plug-in id, and the event domain of both. The NDI plug-in is the model case: an `Input` and a `StreamingService` in the host half, and a pane listing discovered NDI sources in the app half.

**Two protocol packages, not one.** *(Decision 2)* `TingraPlugInKit` must stay importable by the CLI and the daemon, and the CLAUDE.md rule that engine packages are UI-free is what keeps it honest. The app-tier kit imports ExtensionKit and SwiftUI and is linked only by extensions and by the app.

**Vocabulary: registries, not "contribution points" or "extension points".** *(Decision 4)* GLOSSARY.md already says a registry is the seam where plug-ins attach, and that rule scales: the app tier adds a **pane registry**, a **command registry**, a **settings registry** beside the host's input, output, effect, media, and tool registries. Rejected: VS Code's "contribution point" (a second noun for the thing a registry already is, and "contribution" reads as community language Tingra avoids) and ExtensionKit's "extension point" ("extension" beside "plug-in" is two words for one thing). ExtensionKit's own term is unavoidable in the one place it is Apple's API — Tingra *declares an extension point* to the system — and nowhere else; in Tingra prose an app-tier plug-in is still a plug-in. New GLOSSARY terms are **tier** (host tier, app tier), **pane** (a plug-in-contributed view hosted in a sidebar), **command** (a plug-in-contributed menu action), and **descriptor** (the static declaration of a pane, command, or settings pane the app reads before the plug-in runs). **"Tool" stays reserved for MCP tools** — the request that started this plan said "tools", but the word is taken by an agent-facing contract, and reusing it would blur exactly the boundary this phase draws.

### The app tier's process model

**App-tier plug-ins run out of process, always, as ExtensionKit extensions.** *(Decision 12)* The reasons, in order of weight:

- **A crashed notes pane must not take down a live stream.** That is a worse outcome than a crashed linter taking down an editor, and it is the outcome OBS lives with. Third-party UI code never runs in the process that owns the compositor, the mixer, or the stream keys.
- **The system does the hard parts.** Discovery (`AppExtensionIdentity.matching(appExtensionPointIDs:)`), launch, sandboxing, crash recovery, and the remote view (`EXHostViewController`) are macOS 13 API, under the macOS 15 floor. No Disable Library Validation is needed for the app tier; the extension's own signature and notarization cover it.
- **The seam becomes a wire protocol, which is the easiest kind of contract to keep compatible.** An extension built against an older kit keeps working as long as the protocol only gains methods — no ABI, no module interface, no recompilation.
- **Version isolation is free.** Each extension links its own kit version; two extensions built years apart coexist.

The costs, stated plainly: remote views have limits (the SwiftUI environment does not cross, focus and drag and drop need care, sizing inside a resizable sidebar is the item most likely to bite); distribution is heavier (a container app, enabled in System Settings > General > Login Items & Extensions, which the app can present in place through `EXAppExtensionBrowserViewController`); and first-party plug-ins pay the same tax — which is deliberate, see Decision 13.

**One hosting mode, first party included.** *(Decision 13)* VS Code runs its built-in extensions in the extension host; AUv3 hosts treat Apple's own units no differently. Tingra does the same: Notes is Tingra's first extension, embedded in `Tingra.app/Contents/Extensions/`. One mode means one API, one test surface, and first-party pain felt before third parties feel it. The spike checks that an embedded extension is discovered and enabled without a trip to System Settings.

**The link speaks MCP.** *(Decision 14)* CLAUDE.md forbids a second internal RPC protocol, and the rule applies here as written: the connection ExtensionKit hands each side (`makeXPCConnection()`) carries the existing hand-rolled JSON-RPC layer from `TingraMCP` over a new `XPCMessageTransport` — the third `MessageTransport` beside the socket and in-memory ones. Control is `tools/call`, observation is MCP resources with subscriptions, and the handful of app-tier-only methods (`tingra/storage.get`, `tingra/storage.set`, `tingra/event`) are namespaced additions to the same protocol. Consequences worth stating: the app links `TingraMCP` and becomes an MCP server to its extensions (and could later expose the same server on the Unix socket, making the app and `serve` interchangeable to an agent — out of scope, but the door is open); the JSON-RPC message types and `MessageTransport` move out of `TingraMCP` into a zero-dependency `TingraJSONRPC` package so an extension can link them without `TingraHost`; and the app registers `ControlToolsPlugIn` against a real `ToolRegistry` instead of today's `UnusedToolRegistering` stub, which means the stream coordinator behind those tools becomes a host-side type the app and the daemon share.

### Spike findings (2026-09-13)

The spike ran the same day as the approval, as a throwaway `tingra-spike` extension target embedded in Tingra.app with a `Plug-ins` menu, a pane under the Library, and a two-way XPC channel. **All five rows passed.** The extension target and the app hooks were deleted afterwards; the extension point declaration and the embed build phase stayed, because Phase 1 needs them unchanged. What the platform actually does, row by row:

| # | Result | What it changes in the plan |
|---|---|---|
| 1 | **Passed.** The host declares its extension point with a property list named `<identifier>.appextensionpoint` copied into `Contents/Extensions` (the Xcode "ExtensionKit Extensions" copy destination) — one dictionary per point keyed by identifier, `EXPresentsUserInterface` true for a point that hosts panes. No entitlement exists or is needed; without the file, `AppExtensionIdentity.matching` throws `com.apple.extensionKit.errorDomain` code 13. The embedded extension was reported `enabled=1 unapproved=0` and discovered with no System Settings visit; the first discovery after a fresh build took eleven seconds (pluginkit registering the new bundle), every later launch under a second. `pluginkit -m -p com.moonwink.tingra.app.plug-in` lists it. Signed with the app's automatic signing and the sandbox entitlement alone. | `apps/tingra-app/com.moonwink.tingra.app.plug-in.appextensionpoint` is the declaration, kept. Third-party enablement through `EXAppExtensionBrowserViewController` was not exercised (no third-party bundle exists yet); it stays a Phase 3 check. |
| 2 | **Passed.** `EXHostViewController` under `NSViewControllerRepresentable` in the trailing sidebar: the remote `TextEditor`, button, and log drew at the right size, followed the sidebar through a window resize, and rendered dark when the app's appearance preference was dark. The placeholder view showed until the scene activated. Two things the host must do itself: **an `EXHostViewController` does not relaunch its scene after the extension process dies** — it shows the placeholder forever, so the app recreates the host view controller (`.id(generation)`) one second after `hostViewControllerWillDeactivate(_:error:)` reports an error; and a hidden pane's cost was not measured (the pane was always visible). | `PaneRegistry` owns re-hosting with a one-second beat, and `plugin.deactivated` carries the system's reason. Keyboard focus into the remote text editor was **not verified**: the session's automation had no assistive access, so this is Larry's one manual check. |
| 3 | **Passed.** A JSON-RPC `tools/call` over an `NSXPCConnection` from `AppExtensionProcess.makeXPCConnection()`: **390 µs warm round trip**, 10.7 ms including the first connection to an already-running process, 113 ms including a cold process launch (27 ms of it the launch itself). A `kill -9` of the extension produced the connection's interruption and invalidation handlers plus `hostViewControllerWillDeactivate` with `com.apple.extensionKit.errorDomain` code 15; the next command relaunched the process and completed. **One process serves every connection** — the pane's scene and the command connection landed in the same pid. Two platform rules the kit must encode: an XPC connection is established on its *first message*, so a connection the extension only ever pulls on (the pane's) never reaches the extension's `onConnection` until the app sends something — the app opens every connection with a hello; and every closure XPC calls (exported object methods, reply and error handlers, interruption and invalidation handlers) runs on the connection's queue, so under `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` the channel protocol is `nonisolated` and the handlers are `@Sendable`, or the process traps (both processes crashed once this way). | `XPCMessageTransport` sends the MCP `initialize` first. `TingraAppPlugInKit` owns the connection setup so no author meets the isolation trap. `plugin.deactivated` reason comes from the code-15 error. |
| 4 | **Passed.** The pane pulled the program frame's `IOSurface` over XPC at its display's rate: 600 pulls per 10.0 s (60 Hz exactly), 1920×1080, drawn as a `CALayer`'s contents with no copy and one request in flight at a time, so no backlog. The extension process cost about 9 % CPU doing it; the app-side read went through one main-actor hop per pull that Phase 2 removes by reading the relay's lock-guarded frame directly. | A pane can draw program video. Phase 2's `tingra://program` frames resource is pull-based, latest wins, exactly the tee's rule. |
| 5 | **Passed.** Command and pane descriptors were read from the extension's Info.plist (`EXAppExtensionAttributes` → `TingraPlugIn`) at discovery, the `Plug-ins` menu rendered before any command had run, the `tap` preceded the forward, and the command launched the process on demand. `NSWorkspace.urlForApplication(withBundleIdentifier:)` does **not** locate an `.appex`, so the spike read the embedded bundle's path directly. | Manifests stay in Info.plist. Locating a third-party extension's bundle needs `pluginkit`'s answer (the container app's URL plus `Contents/Extensions`) or the first-launch handshake fallback; decided in Phase 3 with the first third-party bundle. |

Two findings outside the table: the `AppExtensionIdentity.matching` sequence is deprecated in macOS 26 in favour of `AppExtensionPoint.Monitor`, but is the only API under the macOS 15 floor and emits no warning there; and Tingra.app's own idle CPU (about 60–90 % with the monitors drawing at 60 Hz unconditionally, a known item in TODO.md) dwarfs anything the extension costs.

## Phase 1 — the app tier and its first plug-in

This is the "first step": a plug-in the host never sees adds a sidebar pane, a menu item, and log lines, and saves what it makes — from its own process.

### The `TingraAppPlugInKit` package

`packages/TingraAppPlugInKit` → `TingraPlugInKit` + `TingraEventBus` + `TingraJSONRPC`; imports ExtensionKit and SwiftUI; sets `defaultIsolation(MainActor.self)` in its manifest, matching the app target (a type that must run off the main actor says `nonisolated`, as in the app). It is the **extension side** of the seam — what a plug-in author links. Its public surface, all documented in TYPES.md when built:

- **Descriptors** *(Decision 5)* — `PaneDescriptor` (`id: PaneID` as `<plugInID>.<name>`, `title`, `systemImage`, `preferredSidebar: SidebarPosition` of `.leading`, `.trailing`, `.bottom`, `sceneID`), `CommandDescriptor` (`id`, `title`, `shortcut: ShortcutDescriptor?` — Codable, since `KeyboardShortcut` is not, `placement: CommandPlacement` with v1's single case `.plugInMenu`), `SettingsPaneDescriptor`. All `Codable`, all read by the app from the extension's Info.plist under `EXAppExtensionAttributes` at discovery, the way VS Code reads `contributes`. The kit provides a `PlugInManifest` type and a build-phase check that the Info.plist decodes, so a typo is a build error, not a silently missing menu.
- **`TingraAppExtension`** — the protocol an extension's `@main` type adopts: ExtensionKit's `AppExtension` with one `AppExtensionScene` per pane and settings pane (each named by the descriptor's `sceneID`), plus the non-UI scene the app connects to for commands and events. The kit owns the boilerplate; an author writes `var panes: [PaneID: some View]` and `func perform(_ command: CommandID) async throws`.
- **`PlugInConnection`** — the extension's client for the app's MCP endpoint over the scene connection: `call(_ tool: String, arguments: JSONValue) async throws -> JSONValue` (Decision 10), `subscribe(_ resource: String)` for observation (phase 2), `event(_ name:params:)` for logging, and `storage` below. One object, handed to the extension when its connection activates.
- **Storage** *(Decision 7)* — two scopes, no secrets, both served by the app because the extension is sandboxed away from the project file:
  - **Project-scoped**: `projectData: JSONValue?` read and `setProjectData(_:)` write, over `tingra/storage.*`. Stored in the project document under a new optional top-level key, `plugInData: [String: JSONValue]?` keyed by `PlugInID` (an optional key, never a version bump — the pre-release rule). A write dirties the document like a layer edit, so notes save with the project and travel with it. Unknown plug-in data round-trips untouched, so a project opened without the plug-in loses nothing.
  - **App-scoped**: `applicationData` read and write, a JSON blob the app keeps at `~/Library/Application Support/Tingra/Plug-ins/<PlugInID>/`, plus the extension's own sandbox container for anything bulky.
  - **Not in scope**: secrets. A plug-in that needs a key (a chat service token) gets a narrowed `SecureStorage` method in phase 2, never a plaintext file.
- **Logging needs no new seam.** `PlugInConnection.event(...)` lands the event on the app's bus with the plug-in's `PlugInID` as its domain; `EventDomain` is already an open, string-backed set for exactly this reason (EVENTS.md). Lines reach `~/Library/Logs/Tingra/Tingra.log` through the existing `FileSink`, OSLog, and the log window — whose domain menu is derived from the lines it has loaded, so a plug-in domain appears the moment the plug-in emits. Plug-ins never format a log line, per the same rule as everything else.

### The app side

The app is the host of the app tier: **its registries, its extension host model, and its MCP endpoint live in the app target for now** *(Decision 8)*, mirroring `TingraHost` owning the registries for `TingraPlugInKit`. If a second front end ever needs them they extract into a package; until then a package would be speculation.

- `AppPlugInHost` — an `@Observable @MainActor` model that discovers identities for the extension point at launch and on the system's change notification (never polling), decodes each manifest, and fills the three registries: `PaneRegistry`, `CommandRegistry`, `SettingsRegistry`. Registration is by descriptor, before any process runs. A malformed manifest is an `error` event naming the extension and the key, and the next extension registers normally.
- **Launch on demand** *(Decision 6)* — an extension's process starts when its pane is first expanded (`EXHostViewController` does this itself), when one of its commands is invoked, or when a phase-2 activation condition it declared is met. `plugin.activated` carries `"tier": "app"` (the host-tier event gains `"tier": "host"`); a process exit is `plugin.deactivated` with the reason, and the pane shows the placeholder view until the next activation — a device disconnect, not an error.
- **The trailing sidebar hosts registered panes.** Today its two panes (layer inspector, Library) are literal children of a `VStack` behind a draggable splitter. Phase 1 makes it a stack of panes: the two existing ones stay first, unchanged in look, and registered panes follow as collapsible sections below the Library, each in shared chrome (a disclosure header carrying the title and symbol, expansion persisted per pane id under `sidebar.<paneID>.expanded`, the `SidebarPreferences` pattern). Uniformity comes from the container, not from asking each author to match it. ## Phase 2 — seams into the engine: observe, then act

A pane that can only show its own data is a widget. The seams that make the app tier *capable* let a plug-in see what the engine is doing and, with care, drive it. Over the MCP link these are **resources** a plug-in subscribes to, each backed by `EngineModel` state that already exists, so the work is deciding the public shape and pinning it with the SemVer policy.

| Resource | What a plug-in sees | Backed by today |
|---|---|---|
| `tingra://session` | stream and recording status, per-destination state and statistics | `EngineModel.streamStatus`, `destinationStates`, `recordingStatus` |
| `tingra://program` | active preset, program and preview shot, tally per input, fade-to-black | `activeShotID`, `previewShotID`, `programInputIDs`, `isFadedToBlack` |
| `tingra://inputs` | the inputs the engine knows, by kind, with connect/disconnect | `cameras`, `displays`, `audioInputs`, `media` |
| `tingra://meters` | per-strip and master levels at meter rate *(built 2026-09-18 as the `tingra/meters` notification, not a resource — Decision 18, seventh slice below)* | `MeterRelay` |
| program and preview frames | `IOSurface` objects over the connection, newest wins, for a pane drawing its own monitor *(built 2026-09-18 as `tingra/frame.next` → `tingra/frame`, eighth slice below)* | `ProgramFrameRelay` (only if spike row 4 passed) |

The rule: **observation exposes value types and identifiers, never `Compositor`, `AudioMixer`, or a registry** — those stay private to the app, as they are now. Agents get every resource for free, since the daemon serves the same protocol.

**Control: plug-ins act on the engine through tools, not a second API.** *(Decision 10)* The MCP tools are already the engine's stable, identifier-keyed control contract (`stream_start`, `stream_stop`, `devices_list`, …). Rather than inventing a parallel surface with its own errors and its own stability policy, a plug-in that wants to take a shot calls the same `shot_take` tool an agent would. One contract, one set of `ErrorIdentifier`s, one place to add authorization later. The tool surface grows the program controls (`shot_take`, `preview_set`, `fade_to_black`) that MCP.md already anticipates.

**Activation conditions** *(Decision 6, continued)* — a descriptor may declare `activation: ["session.started", "input.connected:ndi"]`, VS Code's activation events. The app launches the extension on the first matching event, so a tally-light bridge with no pane still comes alive when the stream starts.

**Declared parameters for every host-tier registration** *(Decision 15)* — `EffectParameter` today gives an effect a settings UI the app renders without the effect knowing SwiftUI exists. The same declaration extends to inputs, outputs, and destination kinds (`ParameterDescribing` on the registered provider), so a host-only plug-in gets a native settings pane with no app half at all — the OBS property pane and the AUv3 generic editor, done once in the app. Most third-party plug-ins will need nothing more than this, which is the point. *(Built 2026-09-15 as the third slice, below.)*

**Secrets:** `tingra/secrets.*` narrowed to the plug-in's own keys (`<PlugInID>.<name>`), Keychain-backed like everything else. *(Built 2026-09-17 as the fourth slice, below.)*

**More app-tier registries:** windows (a plug-in-owned window, for a rundown or a multiview-style surface, one scene each), status bar items, and the leading-sidebar section hosting deferred from phase 1. *(Windows and status items built 2026-09-18 as the fifth slice, below; leading-sidebar hosting still deferred.)*

### Phase 2 as built, first slice: observe, then act (2026-09-14)

The seams landed in the order the heading gives — first what a plug-in can *see*, then what it can *do* — as one slice, verified by the packages' tests and the app's, with the rest of the phase sequenced behind it. What is in:

- **Resources are MCP's own primitive, hand-rolled like the tools.** `TingraPlugInKit` gained the `Resource` protocol beside `Tool` (URI, name, title, description, MIME type, `read()`, and a `changes()` signal stream, the last two defaulting to JSON and to never changing), `TingraHost` a `ResourceRegistry` beside `ToolRegistry`, and `MCPSession` the four methods — `resources/list`, `resources/read`, `resources/subscribe`, `resources/unsubscribe` — plus `notifications/resources/updated`, advertised as `capabilities.resources: {subscribe: true, listChanged: false}` in `initialize`. An unknown URI answers with MCP's `-32002` carrying the URI in `data`. The daemon serves the same methods over an empty registry today, so an agent sees the resources the day the daemon has state worth observing; nothing in `TingraMCP` is app-specific. The plug-in-*contributed* resource seam (`ResourceRegistering` on `PlugInContext`) stays in Phase 4, as planned: this slice needed a registry, not a seam.
- **Three resources, rendered from `EngineModel`, exactly the rule above: value types and identifiers, never the compositor, the mixer, or a registry.** `tingra://session` (stream state with the counters and each destination's own state, recording state with the file), `tingra://program` (presets and the active one, the active preset's shots with ids, origins, and their input ids, the program and preview shots, the tally as `programInputs`/`previewInputs`, `fadedToBlack`), and `tingra://inputs` (every known input: id, name, kind, media, a media file's path). Each is a `ModelResource` in the app: a snapshot closure run on the main actor, and a change stream driven by `withObservationTracking` over exactly what the snapshot reads, re-rendering after each change and signalling only when the document differs — so a follower of the program is woken by a take and never by a meter, and nothing polls. `tingra://meters` and the frame resource are the deferred rows: meters need a rate decision (an updated notification plus a re-read per meter tick is two messages a tick), and frames wait on the IOSurface-over-XPC question spike row 4 left open. **Decided 2026-09-15 (Decision 18): meters are a notification, not a resource.** A session opts in, and the app sends a `tingra/meters` notification carrying the per-strip and master levels inline, coalesced to at most 10 Hz — one message per tick, no re-read — because bending the resource primitive to a meter rate would cost two messages a tick for a value that is stale by the time it is read. Frames stay open behind it. *(Both built 2026-09-18: the seventh and eighth slices, below.)*
- **The program tools, app-owned.** `shot_take`, `preview_set`, and `fade_to_black` register through the same `ToolRegistering` seam every tool plug-in uses, as `ProgramToolsPlugIn` in the app target — not in `TingraMCP`, because only the app has a program: the daemon streams one input through `StreamSession` and has no compositor to take a shot on (ARCHITECTURE.md said as much of `fade_to_black` at the fade-to-black iteration). The `shot` selector follows the input and destination selectors' rule — an exact id wins, else a case-insensitive name that must match exactly one, no index form — with two append-only identifiers, `shotNotFound` and `shotAmbiguous` (CLI.md, "Error identifiers"). The tools act through a `ProgramControlling` seam the model conforms to, so they are tested against a fake with no engine booted. A take made by a tool is the operator's take — the same `EngineModel.take` the switcher button calls, so the compositor's `program.take` reports it — and the tools report no `tap`, which is a click's event, not a call's.
- **The extension side follows a resource with one call.** `PlugInConnection` gained `resources()`, `read(_:)`, and `observe(_:)` — the last an `AsyncStream` that subscribes, yields the document now, re-reads after each updated notification, and unsubscribes when its consumer stops — so a pane showing what is on program iterates it in a `.task` and never polls. Changes coalesce on both sides (newest-one buffering in the resource, the session, and the connection).

What is *not* in this slice, and why, so the rest of Phase 2 can be sequenced without re-deciding it:

- **Stream and recording control in the app** — the app's own `stream_start`/`stream_stop`/`record_start`/`record_stop`. The daemon's `stream_start` takes destinations as arguments and a single input; the app's stream is the program to the project's enabled destinations, so the same tool name would carry different arguments and semantics in the two endpoints. That is a contract decision (one name with an endpoint-dependent schema, or app-specific names such as `program_stream_start`), taken with Larry before any code. The `tingra://session` resource already shows both states, so a plug-in can *observe* the stream today. **Decided 2026-09-15 (Decision 17): app-specific names.** The app registers `program_stream_start`, `program_stream_stop`, `program_record_start`, and `program_record_stop`, taking no destination or input arguments because the project's enabled destinations and the program are what they act on; the daemon's `stream_*` names keep their schemas untouched. One tool name never carries two schemas, so an agent that talks to both endpoints is never surprised. `destinations_list` in the app follows the same rule. *(Built 2026-09-18 as the sixth slice, below — without a destinations tool, which `tingra://session` already answers.)*
- **`devices_list` and `destinations_list` in the app.** Both are `internal` to `TingraMCP` and built over the daemon's registries; the app's `tingra://inputs` resource answers the first, and the second waits on the stream-control decision above (the app's destinations are the project's, not only the operator-global store's).
- **Declared parameters on every host-tier registration (Decision 15), the narrowed secrets method, windows and status bar items** — each its own slice, in that order. Activation conditions were the second slice, declared parameters the third, the secrets method the fourth, and windows and status items the fifth, all below.

### Phase 2 as built, second slice: activation conditions (2026-09-15)

The launch-on-demand list (Decision 6) gained its third entry: a plug-in's process now starts when a bus event meets an **activation condition** its manifest declares, beside a pane shown and a command invoked — so a tally-light bridge with no pane comes alive when the stream starts. What is in:

- **A condition is an event name, optionally qualified by one param** *(approved 2026-09-15)*. `ActivationCondition` in `TingraAppPlugInKit`, written in the manifest's `activation` list as one string: `stream.started`, or `device.connected:kind=camera`. The name is matched exactly against the event's `name`, whatever its domain, so a plug-in wakes on another plug-in's event as readily as on the engine's; the qualifier compares the named param's string form, so `attempt=2` matches an `int`. The plan's example above spelled it `input.connected:ndi`; the build uses the events the bus actually carries (`device.connected` with its `kind`, `stream.started`, `recording.started`, `program.take`, …) and names the param explicitly, because the bare-value form would have had to guess which param an author meant. A malformed condition is a `PlugInManifestError.malformed` naming the text, a repeated one `duplicateActivation` — reported at discovery like every other manifest fault, never a condition that silently never fires.
- **The app watches the bus once, for everyone.** `AppPlugInHost` drains `EventBus.events()` in one task and asks an `ActivationTable` — every discovered plug-in's conditions indexed by event name — about each event: one dictionary lookup per event, nothing at all when no plug-in declared a condition, a plug-in woken once per event however many of its conditions the event meets. Never a poll: the bus is already the app's change stream.
- **Waking is the command connection's launch, plus a request.** A match calls `AppPlugInLink.activate`, which opens the `process` session through `AppExtensionProcess` if none is open — the same path a command takes, so the process then stays up until the app lets go, VS Code's semantics — and sends `tingra/activation` carrying the condition and the `EventBusEvent` itself as JSON. `plugin.activated` names the `condition` that launched the process. The extension answers through `TingraAppExtension.activated(by:event:using:)`, a new requirement with a do-nothing default, so a plug-in woken only to follow `tingra://session` writes no handler; a handler that throws is a `plugin.activation` error carrying the plug-in, the condition, and the event name — the app tier's counterpart of the host tier's report of the same name.
- **Every match is reported, not only the first** *(approved 2026-09-15)*. The first launches the process; each later one arrives as the same request. That is a superset of the plan's "launches the extension on the first matching event", chosen because a running tally bridge that never heard about the second `stream.started` would have to follow the session resource just to learn what it already declared an interest in — and a request per matching event is bounded by what the author chose to declare.
- **`EventBusEvent` gained a public initializer** in `TingraEventBus`, additive: the extension side decodes the event from the wire through `Codable`, and the tests build events by hand.
- **Notes declares no condition.** It has nothing to do until its pane is shown, and a condition it did nothing with would launch a process for no one. The seam is proved by the kit's tests over the in-memory transport pair (the request parsed, the handler run with the condition and the decoded event, a throwing handler answered as an internal error, a missing event as invalid params) and by the app's tests of the table. **Not yet verified in the running app:** a throwaway `plugin.discovered` condition on Notes was built to watch the process launch from a bus event, but Larry's own Xcode debug instance was running at the time and the rule is never to kill it or run a second instance against his live project, so that one check — `plugin.activated` carrying `condition`, then the extension's answer — is the manual step left open, as keyboard focus was in Phase 1.

Tests: `TingraAppPlugInKit` 25 → 39, the app +4 (`ActivationTable`).

### Phase 2 as built, third slice: declared parameters (2026-09-15)

Decision 15 landed: the declaration effects have made since roadmap step 7 is now the one every host-tier registration makes, and the app drew its first settings pane from it for a plug-in that wrote none of the pane. What is in:

- **One descriptor, one protocol** *(Decision 19, approved 2026-09-15)*. `EffectParameter` became **`Parameter`** and `EffectColor` **`ParameterColor`** — the house style names the thing, not its first user (`Input`, `Tool`, `Resource`) — with the old names kept as deprecated aliases and every first-party use moved in the same change; the kit has no tag yet, so the aliases cost nothing and bind no one. The new `ParameterDescribing` protocol carries the one requirement, `parameters`, defaulted to empty, and `Input`, `StreamingServiceProvider`, `RecordingServiceProvider`, `AudioEffectProvider`, and `VideoEffectProvider` all refine it — the effect providers by moving their existing requirement up, so every effect compiles unchanged. `Parameter` gained `value(in:)`, `color(in:)`, and `clamped(_:)`, the three reading rules every control and every conformer had been spelling out by hand.
- **Values live where each registration's target already is; there is no second value seam** *(approved 2026-09-15)*. An effect's chain slot carried its payload already (`EffectConfiguration.parameters`). An `Input` gains `setParameters(_:)`, defaulted to nothing and called live — before or after `start()`, so a running generator retunes without a stop; an omitted key means its declared default, an undeclared key is ignored. A streaming provider's values ride on the `Destination` it is started with, a recording provider's on the `RecordingFile`: both gained `parameters`, defaulted empty, so `start(to:)` is untouched and no provider's `make…` signature changes. A `MediaInputProvider` declares nothing of its own — its per-file settings are the created input's, through the same `Input` path.
- **The app stores an input's values per project** *(approved 2026-09-15)* (`Project.inputParameters`, keyed by input id, an optional key within v1 like `plugInData`): per project rather than per preset because an input's settings describe the input, the way its media list does, where a strip's level describes its place in one preset's mix. It hands them to every declaring input with each device-list rebuild — a device that reconnects is a fresh instance that knows nothing of the project — and hands an empty payload to a declaring input the project has no entry for, so opening another project never leaves an input tuned by the last one. Edits apply live and in order (one chained task, so gesture-rate edits cannot race to the registry) and autosave debounced, exactly as an effect parameter's do.
- **The pane is generic, and the tone is the proof.** `InputParametersView` draws a slider paired with the shared value field per number parameter and the shared color well per color parameter, from the descriptors alone; the channel strip shows an **Input Settings** button only for an input that declares any, so a microphone's strip is unchanged. `ToneGenerator` declares `frequencyHertz` (20 Hz–20 kHz, logarithmic, 440) and `levelDecibels` (−60…0 dB, defaulting to the half amplitude it has always had), retuning phase-continuously at the next buffer: the synthesizer moved from a sample counter to a running phase accumulator so a frequency change bends the wave instead of breaking it.
- **Sliders honor the declared scale now** *(approved 2026-09-15)*. `ParameterScale` (pure, tested) maps a slider's `0…1` travel through `Parameter.Scale`, so 440 Hz sits near the middle of the tone's frequency slider rather than at two percent of it. The two effect chain editors take the same mapping — they had drawn the high- and low-pass cutoffs linearly across 20 Hz–20 kHz despite both declaring `.logarithmic`, which the descriptor had promised and the app had ignored.

Not in this slice, and why: the **destination editor and the recording preferences drawing provider parameters** — HaishinKit and the recorder declare none, so there is nothing to draw until the NDI output declares a stream name, and where the values go (`Destination.parameters`, `RecordingFile.parameters`) is already fixed, so that is UI work with no seam question left; and a **settings hook for video inputs** — no first-party video input declares a parameter, and the layer inspector is where the same popover goes when one does. The `tingra://inputs` resource does not yet list an input's parameters; it joins them when an agent has a reason to read them.

Tests: `TingraPlugInKit` 47 → 57, `TingraGeneratorPlugIns` 77 → 81, `TingraComposition` 222 → 224, the app 616 → 622.

### Phase 2 as built, fourth slice: secrets (2026-09-17)

Decision 7's deferred half landed: a plug-in that needs a key — a chat service's token — has the narrowed secure-storage method, and still no plaintext file. What is in:

- **Two methods, one namespace.** `tingra/secrets.get` and `tingra/secrets.set` join the `tingra/*` methods (`AppTierMethod.secretsGet`/`secretsSet`, with `SecretParam.name`/`value`): a `name` (`token` — not itself a secret, free to appear in events) and, on a set, a string `value` or `null` to remove. `PlugInConnection.secret(named:)` and `setSecret(_:named:)` are the extension's calls. The plug-in id is the connection's, never a param — the storage rule — so the app files each secret in the engine's own `SecureStorage` (the Keychain, the same access group as the stream keys) under `plugin:<PlugInID>.<name>` (`PlugInSecretStore`), the plug-in's namespace the way a pane id is `<plugInID>.<name>`. A plug-in reads and writes its own secrets and nothing else: never another plug-in's, never a stream key, whose items carry `DestinationStore`'s `destination:` prefix.
- **A refusal is an answer, not a drop.** The storage scopes swallow a failed app-scope write and report it, because a lost preference is recoverable; a secret the Keychain refused is not, so `secrets.set` (and a refused `get`) answers with a JSON-RPC internal error naming the operation, the name, and the store's own reason — `OSStatus -34018` on an unsigned build, the refusal the stream keys meet — and the app reports `plugin.secrets` under the plug-in domain with the same fields. Neither carries the value: the handler is the one place a value passes through, and it goes into no event, error, or log, EVENTS.md's rule for stream keys applied once more. A missing or empty name, or a value that is not a string, is invalid params.
- **The Data settings pane tells them apart.** Plug-in secrets share the Keychain service with the stream keys, so the pane gained two kinds beside **Stream Keys**, which now counts only the keys: **Plug-in Secrets** (the `plugin:` items, in the Keychain) and **Plug-in Data** (the app-scoped files under `~/Library/Application Support/Tingra/Plug-ins`, which Remove All Data had until now left behind — it removes the folder, so a first run finds no folder again). Remove All Data clears both.
- **Notes stores no secret.** It has nothing to keep secret, and a token stored for no one is a token to leak. The seam is proved by the kit's tests over the in-memory transport pair (a round trip by name, a removal, a refused store surfacing as the app's error) and the app's over the handler (the round trip, the narrowing to the connection's plug-in, the invalid params, the refusal and its event without the value) and the store; the real Keychain path is the one `KeychainSecureStorage` already runs for the stream keys, with no new query shape.

Not in this slice: a listing of a plug-in's secret names — a plug-in knows the names it chose, and a listing would be the first method to say anything about a secret not asked for by name; it joins when a plug-in with dynamic names (one token per channel) needs it. The host tier's `PlugInContext` still has no secure-storage seam: no host-only first-party plug-in needs a secret, and the NDI output that first might is a Phase 3 bundle.

Tests: `TingraAppPlugInKit` 39 → 40, the app 622 → 632.

### Phase 2 as built, fifth slice: windows and status items (2026-09-18)

The app tier gained its next two registries, and both were watched working in the running app. What is in:

- **A window is a pane in a window of its own.** `WindowDescriptor` (id, title, scene) joins the manifest's `windows` list. Its id is a `PaneID`, in the one id space panes and settings panes already share and under the same namespacing rule, because a window is the third kind of hosted scene and not a new kind of thing: `TingraAppExtension.pane(for:)` answers for it, the kit makes its scene beside the others, and the app's hosting path — the connection opened when the scene activates, the session closed when it goes, the host view controller recreated a beat after the process died — is the pane's, unchanged (`PaneRegistry.plugIn(hosting:)` replaced the two lookups that had each spelled out "a pane or a settings pane"). The app supplies the window: one `WindowGroup(for: PaneID.self)` scene for every plug-in's windows, titled from the descriptor, 640×480 until the operator sizes it, listed in the Window menu and restored by the system like any other. One window per id: opening one that is open brings it forward, the rule Multiview and the log follow.
- **A command opens it** — `CommandDescriptor.showsWindow`, the twin of `showsPane`. The menu item emits its `tap`, opens the window, then forwards the command, so a plug-in's "Show Rundown" costs no round trip and carries its shortcut and its event like every other command. The open happens in `PlugInCommands`, not the host, because `openWindow` is an environment action only a view can take; and only for a window the *same* plug-in declared, so no command opens another plug-in's window by naming its id. A window restored at launch draws before discovery has run, so `PlugInWindowView` reads the registry on every draw: it fills in the moment its plug-in is discovered, and says **Plug-in Unavailable** when the plug-in is gone with its window left open.
- **A status item is declared by the plug-in and drawn by the app.** `StatusItemDescriptor` (a `StatusItemID` unique within the plug-in, a title, a symbol) in the manifest's `statusItems`; `tingra/statusItem.set` (`item`, `text`) and `PlugInConnection.setStatusText(_:for:)` give it its text. **No extension scene is hosted for it** — a remote view for a dozen points of text would launch a process to draw a word — so it is the field's data-driven half (PLUGINS.md, "What the field teaches": VS Code's status bar items), and Decision 5's uniform chrome at its smallest: the reading is the bar's own caption type in the secondary style, and a plug-in cannot shout over *Recording* or *Live*. Plug-ins' readings sit at the **trailing** end; the app's three keep the leading edge to themselves. The title is the tooltip (with the plug-in's name) and what VoiceOver says before the text.
- **It reports and never acts, and never outlives its process.** No click, no command: GLOSSARY.md's rule for the bar holds for a plug-in's reading as for the app's own. An item is on the bar only while it has a text (`null` or an empty string takes it off); `StatusItemRegistry` drops a plug-in's texts when its last connection closes, since nothing is left to keep them true; a text is cut at 40 characters, once, in the registry. The plug-in id is the connection's, so a plug-in sets its own items and no other's, and an item the manifest does not declare is invalid params naming the fix. A plug-in with nothing but a status item is woken by an activation condition — the tally bridge's `stream.started` — which is what that slice was for.
- **Notes declares neither.** It has no second surface to show and nothing to report. The seams are proved by the kit's tests (the manifest's two lists, the shared id space, `showsWindow`, the set call over the in-memory pair and the app's refusal of an undeclared item) and the app's (both registries, the handler's narrowing and invalid params). **Verified in the running app, 2026-09-18**, with a throwaway window, status item, and command on Notes, reverted afterwards: `plugin.discovered` carried `windows=1 statusItems=1`; the command's `tap` was followed by the window, titled from the manifest and drawing the extension's scene; the status bar showed the reading the extension set; a second invocation brought the same window forward rather than making another; no error was logged.

Not in this slice: **leading-sidebar hosting**, still deferred — every pane is hosted in the trailing sidebar whatever it prefers, and moving one is the operator-layout work (placement is a preference, the operator's layout wins) that has no second pane to need it yet. A status item's **symbol and tint are fixed by the manifest**: a per-state symbol is an additive optional param when a plug-in needs one. A window has **no declared size**; one scene serves every plug-in's windows and the system keeps each window's frame once the operator has set it.

Tests: `TingraAppPlugInKit` 40 → 46, the app 632 → 640.

### Phase 2 as built, sixth slice: stream and recording control (2026-09-18)

Decision 17 landed: a plug-in or an agent can put the program on air and roll a recording, through four app-owned tools beside the switcher's three. What is in:

- **`program_stream_start`, `program_stream_stop`, `program_record_start`, `program_record_stop`**, registered by the same `ProgramToolsPlugIn` through the same `ToolRegistering` seam, taking **no arguments**: the project's enabled destinations and the program are what they act on, the recordings folder and container are the operator's settings, and the stream keys are read from the Keychain by `EngineModel.startStreaming()` exactly as the toolbar button's are — so a key is never an argument, and a plug-in never chooses where a file is written. They call the very methods the toolbar's buttons call, so `stream.started`, `recording.started`, and the rest report them, and like the switcher's tools they report no `tap`, which is a click's event.
- **Each tool names a state, not a toggle** *(for veto)*. Starting while on air, or stopping while off, is **not an error**: the tool answers the state with `changed: false` and does nothing. The daemon's `stream_start` refuses a second start because it would be a *different* stream — another input, other destinations; the app's start can only ever mean the one program to the project's destinations, which is already what is happening. And the operator shares these controls: a plug-in that asks for the stream the operator started a second ago has what it asked for.
- **The result is `tingra://session`'s own shape.** `{"stream": {"state": …}, "changed": …}` and `{"recording": {"state": …, "path": …}, "changed": …}`, the state members rendered by the same two functions the resource uses (`EngineResources.streamState`, `recordingState`), so a caller reads one shape from the call and from the resource it then follows. A start returns once the session is **starting**, not once it is live — the stream's fate (live, reconnecting, a destination that refused) is the resource's to report, never a second waiting protocol inside a tool. `program_record_stop` names the file it closed even though the model has let go of it by then.
- **Errors reuse the identifiers there are.** Nothing enabled with a usable URL is `destinationNotFound` — widened in CLI.md from "no saved destination matches a selector" to cover "the project has no destination to stream to", the same fact from the app's side — with a message naming the Streaming settings; a start that settles on an error at once is `pipelineError` (no output for a URL's scheme) or `recordingFailed` (the folder could not be created, the volume has no room), carrying the model's own message. No new identifier.
- **No `program_destinations_list`.** `tingra://session` already lists the project's destinations with each one's id, name, URL, enabled flag, and live state; a tool saying the same would be a second contract for one fact.

The tools act through a `ProgramOutputControlling` seam the model conforms to, the twin of `ProgramControlling`, so they are tested against fake outputs with no engine booted. **Not verified against a live stream**: the tools call the two methods the toolbar has called since step 7, and nothing in the app yet calls a tool — the first real caller is a plug-in or an agent on the app's endpoint.

Tests: the app 640 → 651.

### Phase 2 as built, seventh slice: meters (2026-09-18)

Decision 18 landed: a plug-in's pane can draw a meter, and a loudness logger can keep one, from the mix's own readings. What is in:

- **A connection opts in, and the levels arrive inline.** `tingra/meters.subscribe` and `tingra/meters.unsubscribe` are requests answered `{}` — the shape of `resources/subscribe`, so a refusal has somewhere to go — and the app then sends that connection `tingra/meters` notifications: `{"time": …, "strips": {"<inputID>": {"peak": …, "rms": …}}, "master": {"left": {…}, "right": {…}}}`. One message a window, nothing re-read. The subscription is the *connection's* — a pane's, not the plug-in's — and ends with an unsubscribe or the connection; subscribing twice is one subscription. `plugin.meters.subscribed` and `plugin.meters.unsubscribed` (with `reason`: `unsubscribed` or `closed`) are the control-plane record; no level is ever an event.
- **At most ten a second, driven by the mix and never by a timer.** `MeterFeed` sits beside `MeterRelay` on the model's meter drain: each mix block is folded into every follower's **window**, a signal wakes the follower's task, the task sends the window and then waits out a tenth of a second while the next one fills. No block, no wake-up — nothing polls, and a stopped mixer sends nothing. With no follower a block costs one lock.
- **A window keeps what a meter is for** *(for veto)*. A **peak** is the largest of the window's block peaks, so a hot sample between two notifications is never lost — the reason `MeterRelay` folds its holds per block. An **RMS** is the root of the mean of the blocks' squared RMS, the window's own loudness, every mix block being the same length. The strips are the **latest block's**: a strip that left the mix mid-window is not reported. Strip levels are **pre-fader**, the master's **post-fader** left and right — exactly what the app's own meters show.
- **Levels are linear sample magnitudes, not decibels** *(for veto)*: `0` is silence, `1` is full scale, a peak above `1` is an over. Silence has no finite dBFS figure for JSON to carry, and the engine's readings are linear already; `MeterLevel.decibels(_:)` converts for display. Ballistics — attack, decay, hold — are the reader's, as they are the app's own at draw time: the app sends raw windows.
- **The extension follows them with one call.** `PlugInConnection.meters()` is an `AsyncStream<MeterLevels>`: the first follower subscribes the connection, the last to stop unsubscribes it, the newest window wins, and a notification that does not read is dropped — the next is a tenth of a second away.
- **The session gained the one thing a handler lacked: a way to speak first.** `SessionMethodHandler` has two new requirements with do-nothing defaults — `sessionOpened(notifier:)`, handing over a `SessionNotifier` that writes a notification to the session's peer, and `sessionClosed()`, where whatever the handler started ends. The daemon's sessions have no handler and are untouched; **the daemon serves no meters**, having no mixer.

Not in this slice: **held peaks** (the app's peak-hold readout is the operator's, reset by a click; a plug-in keeps its own from the windows), and **a rate the subscriber chooses** — ten a second is the ceiling Decision 18 set, and a param asking for fewer is additive when someone needs it. **Not verified in the running app**: Larry's own Xcode debug instance was running, and the rule is never to kill it or run a second against his live project. The path is proved by the kit's tests over the in-memory pair and the app's over the feed and the handler.

Tests: `TingraMCP` 137 → 138, `TingraAppPlugInKit` 46 → 57, the app 651 → 664.

### Phase 2 as built, eighth slice: frames across the boundary (2026-09-18)

Spike row 4's finding became a seam: a plug-in's pane can draw the program or the preview from the app's own frames, with no copy. What is in:

- **The surface rides beside the JSON, in the same message** *(Decision 21, for veto)*. An `IOSurface` cannot be written into JSON, and a second channel for pixels would be the second RPC protocol CLAUDE.md forbids. So `XPCMessageChannel` gained `deliver(_:surface:)` — one JSON-RPC payload with a surface attached, which XPC passes between processes as a kernel handle — and `TingraJSONRPC` a `SurfaceMessageTransport` refinement (`readSurfaceMessage()`, `writeMessage(_:surface:)`) that the XPC and in-memory transports adopt and the socket transport cannot. The payload still says everything: the method, the bus, the time. `SessionNotifier.notify(_:params:surface:)` is the app's way to send one; over a transport that cannot carry a surface it sends nothing, rather than a notification describing pixels that never arrived.
- **Delivery is demand, one frame at a time** *(for veto)*. The extension sends `tingra/frame.next` (`bus`: `program` or `preview`), answered `{}` at once; the app sends `tingra/frame` (`bus`, `time`, `empty`, and the surface) as soon as the bus has a frame **newer than the last this connection was sent** — which may be immediately — and only that frame's arrival prompts the next demand. One demand per bus per connection is ever outstanding, so frames cannot queue behind a slow reader, the newest wins, nothing is sent twice, and nothing polls: exactly the tee's `bufferingNewest` rule, held across the process boundary. The spike *pulled* — a request whose response carried the surface; the build does not, for two reasons. `MCPSession` answers a connection's requests in order, so a pull held until the next frame would stall every tool call behind it, forever on an empty preview; and a surface in a *response* would thread attachments through the session's whole answer path, where a notification needs one method on the notifier.
- **The relays number their changes.** `ProgramFrameRelay` — the very holders the app's program and preview monitors sample — counts every store and every emptying, and `next(after:)` answers at once when the relay has moved past a number and otherwise suspends until it does. `RelayFrameFeed` surfaces the frame's own `IOSurface` (`CVPixelBufferGetIOSurface`; the working format is IOSurface-backed by convention, and a buffer that is not is reported once per session as `plugin.frames` and skipped). No second tap on the compositor, and with nobody waiting a stored frame costs an empty-dictionary check. **An emptied bus is a change too**: preview with nothing staged arrives as `empty: true` with no surface, so a plug-in's monitor blanks when the app's does. `plugin.frames.started` names the plug-in and the bus on a connection's first demand, so the log says who is drawing video; no frame is ever an event.
- **The kit hides the protocol.** `PlugInConnection.frames(_:)` is an `AsyncStream<BusFrame>` that circulates the demand while it has a consumer and lets it lapse when the last one stops (no unsubscribe exists or is needed); `BusMonitorView(connection:bus:)` is the ready-made monitor — each surface becomes a layer's contents, aspect kept, over black — following only while it is on screen.
- **Program and preview, full size, the working format.** A frame is the program format's size in 32-bit BGRA, BT.709 — what the monitors draw, after fade to black for program. Input frames and multiview are not offered: nothing has asked, and an input's frames raise the TCC question (a plug-in seeing a camera the operator granted to Tingra) that program video, already composed by the operator, does not.

**The surface is shared memory, and that is a trust decision** *(for veto)*. No copy means the plug-in's process maps the very buffer the compositor rendered, which the tee hands to the stream and the recording in the same instant — and an `IOSurface` handle cannot be made read-only. A first-party plug-in is trusted not to write to it, and the kit's documentation says never to; a hostile third-party extension *could* scribble on a frame before it is compressed. The mitigation, if third parties are to be given frames in Phase 3, is one GPU blit per followed bus into a surface the app owns and the pipeline never reads — a copy, but of a frame already rendered, only while a plug-in is following. It is not built, because today every extension is embedded and first-party; it is the question to settle before the enablement sheet admits a stranger.

**Not verified in the running app** — the same reason as the seventh slice. What is proved: a surface crosses a real `NSXPCConnection` as the same surface (`IOSurfaceGetID` equal on both ends, `TingraJSONRPC`'s transport test over an anonymous listener); the demand protocol end to end over the linked in-memory pair (the kit) and against real relays and real IOSurface-backed pixel buffers (the app's handler tests); and spike row 4 drew 1920×1080 at 60 Hz this way for about 9 % of a core. The manual check left open: a throwaway `BusMonitorView` in Notes' pane beside the app's own program monitor.

Tests: `TingraJSONRPC` 11 → 13, `TingraAppPlugInKit` 57 → 62, the app 664 → 675.

## Phase 3 — bundles, extensions, and versions

The external bundle loader is the last item of roadmap step 10 and the moment `TingraPlugInKit` tags 1.0.0. It is now a **host-tier-only** artifact: the app tier needs no loader, because ExtensionKit discovers, launches, and isolates extensions. This plan adds:

- **What a third party ships: an app containing an extension.** macOS discovers extensions only inside a registered application bundle — a `.appex` dropped in a folder is invisible to the system — so an app-tier plug-in is, by construction, a container app the user installs. The container app never has to be running: Tingra asks the system for extensions matching its extension point, the system launches the extension's own sandboxed process on demand and tears it down when Tingra lets go, and the container's job ends once it is on disk (a first launch is the conventional way to be sure the system has registered it). Most AUv3 developers ship a shell app whose only job is to hold the extension and say "installed", and that pattern is fine here. For a plug-in with both halves the container app earns its keep: on first run it copies the host-tier bundle into the plug-in folder the loader scans, so one install delivers both tiers. Host-only plug-ins remain a bare bundle in the folder; app-only ones are the container app and its extension. The plug-in id in the bundle's Info.plist and in the extension's manifest must match; the app reports a mismatch as an `error` naming both. **What the user sees:** a first-party extension embedded in Tingra.app needs no step at all (spike row 1 confirms); a third-party extension is disabled until enabled, once, in the sheet Tingra presents through `EXAppExtensionBrowserViewController` — one click, inside Tingra, never a trip to System Settings unless the user prefers it. There is no plug-in host application in the VS Code sense for anyone to launch or manage; the per-extension process the system spawns is visible in Activity Monitor and nowhere else.
- **Both kits tag 1.0.0 together** *(Decision 11)*. The app-tier contract is descriptors plus a wire protocol, which is why it can be pinned at the same time as the ABI-bound host kit without fear. The JSON-RPC method set is versioned by the MCP protocol-version handshake already in the layer; `swift package diagnose-api-breaking-changes` runs against both kit tags in CI, and a method or resource, once shipped, is append-only like a tool name.
- **Isolation is a tier property, and now a clean one.** App-tier code is out of process by construction. The XPC candidacy ARCHITECTURE.md records for host-tier outputs and automation stays a future option — `AppExtensionProcess` shows the platform can launch a non-UI extension and hand back a connection, which is one way to do it when the day comes.
- **Version negotiation per tier, never a crash**: a bundle whose host-tier major is incompatible is refused with an `error` naming both versions and the fix; an extension whose manifest declares an app-tier major the app does not speak is listed in the enablement sheet as needing an update, and never launched.

**Where this stands with Apple.** The app tier is the architecture Apple built for exactly this case: ExtensionKit exists so a third-party app can host third-party code the way Apple's own apps host Audio Units, Xcode source editor extensions, and Safari extensions — sandboxed, system-launched, remote-viewed. Nothing in it needs a private API or a restricted entitlement beyond the extension-point declaration, which Tingra's existing provisioning already accommodates if it turns out to be profile-bound (spike row 1 checks). It is also Mac App Store-compatible should that ever matter. The host tier is the part Apple tolerates rather than promotes: loading third-party bundles in process requires the Disable Library Validation entitlement the app already carries, which notarization accepts and every DAW and OBS rely on, but which the App Store would not. Two rules keep it on the right side of Gatekeeper: the loader accepts only signed bundles, and a quarantined third-party bundle must itself be notarized, because since macOS 10.15 Gatekeeper checks plug-ins a notarized app loads. Capture stays in process for TCC attribution as ARCHITECTURE.md already decided; if outputs or automation ever move out of process, `AppExtensionProcess` is Apple's sanctioned way to do it. The honest risk is not disapproval but thin adoption: ExtensionKit has few third-party hosts and sparse examples, which is why phase 0 is a spike and not a checklist.

NDI follows as the first out-of-repo plug-in with both halves.

## Phase 4 — breadth: the host seams still missing

The host tier's registries cover capture, generation, media, effects, output, recording, and tools. GLOSSARY.md promises more than the code delivers, and VS Code-level capability is a matter of how many of these exist — OBS's list is the yardstick. In rough order of demand:

| Seam | Registers | Why a plug-in wants it |
|---|---|---|
| `TransitionRegistering` | a `Transition` implementation (GLOSSARY says plug-ins add transitions; today cut, dissolve, and the shader transitions are built in) | wipes, stingers, a branded transition |
| `SinkRegistering` | an `EventSink` | ship events elsewhere: a Discord/Slack notifier, a tally-light bridge listening to `program.take`, a metrics exporter — the same seam the log file uses |
| MCP resources and prompts from plug-ins | beyond tools, the other two MCP primitives | an agent reading the rundown a plug-in maintains |
| `DestinationKindRegistering` | a destination preset kind (URL template, key rules, probe) | a service Tingra has never heard of, with its own probe |
| `SnapshotExporting` | a snapshot destination | post a snapshot to a service |
| `AudioMonitorRegistering` | an `AudioMonitor` | a plug-in-provided monitor path (network audio) |
| Audio Unit hosting (`TingraAudioUnitPlugIns`, first party) | an `AudioEffectProvider` per effect component (`aufx`, `aumf`) that `AVAudioUnitComponentManager` discovers; the wrapper hands the mixer's block — deinterleaved float32 at the mix rate, AU's canonical macOS format — straight to the unit's render block | the AU build of every commercial VST plug-in on a Mac, through the existing effect seam, with no third-party dependency; VST3 itself would mean Steinberg's C++ SDK (GPLv3 or Steinberg's own agreement) and VST2 has been unlicensable since 2018 |

The Audio Unit row rides on the plan's earlier decisions: AUv3 units run out of process by default and AUv2 units can too (`.loadOutOfProcess`, macOS 10.15+), so out of process is the default and in process is the Disable Library Validation path the app already carries; `AUParameterTree` maps onto Decision 15's declared parameters; the unit's `fullState` persists as one opaque key in the effect configuration, the fullState-saved-by-host pattern from the AUv3 precedent; the unit's view controller is hosted in the app tier, never in the engine. Instruments (`aumu`) are a generator, not an effect, and wait. **The latency note:** `AudioEffect` reports no latency today, and a look-ahead limiter or linear-phase EQ adds tens of milliseconds that the A/V sync model in CLOCK.md must know about. Before any third-party unit is trusted in the program mix, the seam grows an optional `latency` requirement (seconds, default zero) that the mixer sums per strip and the compositor's sync accounts for — additive, so within the 1.0.0 stability rules.

Each follows the established pattern exactly: capability protocol plus registering protocol in `TingraPlugInKit`, registry in `TingraHost`, declared parameters per Decision 15, a first-party plug-in that dogfoods it, rows in the ARCHITECTURE.md tables.

## What does not change

- The host/plug-in boundary test (ARCHITECTURE.md): if removing it breaks plug-ins in general it is host; the app-tier registries and the extension host model are host in that sense, and the panes are plug-ins.
- The event bus is the only logging path; the clock is injected; secrets stay in the Keychain.
- One `PlugInID`, one event domain per plug-in, whatever its tiers.
- `TingraPlugInKit` never imports SwiftUI, AppKit, or ExtensionKit.
- One internal RPC protocol. The app tier is served by the MCP layer, not beside it.

## Decisions to veto

1. A plug-in has up to two halves, host tier and app tier; the host tier stays in process.
2. Two protocol packages: `TingraPlugInKit` (headless, unchanged) and `TingraAppPlugInKit` (ExtensionKit + SwiftUI, the extension side).
3. One `PlugInID` across tiers, one event domain, one container app for a plug-in with both halves.
4. Vocabulary: registries, tiers, panes, commands, descriptors. No "contribution point"; "extension point" only where it names Apple's API. "Tool" stays MCP.
5. Panes, commands, and settings panes are declared as Codable descriptors in the extension's manifest; the app supplies uniform chrome; placement is a preference, the operator's layout wins.
6. Plug-in commands live under a "Plug-ins" menu in per-plug-in submenus; the app emits the tap; extensions launch on demand (pane shown, command invoked, declared activation condition).
7. Storage is project-scoped JSON in the document plus an app-scoped blob, both served by the app; secrets wait for a narrowed Keychain method. *(The method landed 2026-09-17: `tingra/secrets.get`/`set`, narrowed to the connection's plug-in under `plugin:<PlugInID>.<name>` in the engine's Keychain-backed store.)*
8. App-tier registries, the extension host model, and the MCP endpoint live in the app target until a second front end needs them.
9. Notes, an extension target embedded in Tingra.app, is the first-party proof.
10. Plug-ins control the engine through the MCP tools (`tools/call`), never a parallel API.
11. Both kits tag 1.0.0 with the bundle loader; the app-tier wire protocol is append-only from then on.
12. App-tier plug-ins run out of process, always, as ExtensionKit extensions.
13. One hosting mode: first-party app-tier plug-ins are extensions too, embedded in the app bundle.
14. The app-to-extension link speaks the existing MCP JSON-RPC layer over an `XPCMessageTransport`; the message types move to a zero-dependency `TingraJSONRPC` package.
15. Declared parameters extend from effects to every host-tier registration, so a host-only plug-in gets a native settings pane without an app half.
16. Phase 0, the ExtensionKit spike, gates phases 1–3; its five rows carry their fallbacks.
17. Stream and recording control in the app are app-owned tools with their own names (`program_stream_start`, `program_stream_stop`, `program_record_start`, `program_record_stop`); a tool name never carries an endpoint-dependent schema *(approved 2026-09-15; built 2026-09-18, each tool naming a state rather than a toggle — for veto)*.
18. Meters reach a plug-in as an opt-in `tingra/meters` notification with the levels inline, capped at 10 Hz — never a resource re-read per tick *(approved 2026-09-15; built 2026-09-18 — linear levels, a window's peak the largest of its blocks', its RMS the blocks' own, for veto)*.
19. The declared-parameter descriptor is `Parameter` and its color value `ParameterColor`, one pair for every registration, with `EffectParameter`/`EffectColor` kept as deprecated aliases; values live where each registration's target already is — the chain slot, `Input.setParameters`, `Destination.parameters`, `RecordingFile.parameters` — never a second value seam *(approved 2026-09-15)*.
20. A plug-in's window is a pane hosted in a window of its own — a `PaneID`, `pane(for:)`, the pane's hosting path — opened by a command that names it (`showsWindow`), one window per id. A status item is declared in the manifest and drawn by the app from a text the plug-in sets (`tingra/statusItem.set`): no hosted scene, no click, trailing end of the bar, gone when the plug-in's last connection closes *(built 2026-09-18, for veto)*.
21. A bus's frames reach a plug-in as the app's own `IOSurface`, attached to a `tingra/frame` JSON-RPC notification in the same XPC message — never a second channel — and only on demand: one `tingra/frame.next` per frame, one outstanding per bus per connection, so the newest wins and none queue. Program and preview only. The surface is shared memory; a blit into an app-owned surface is the mitigation to decide before third-party extensions are admitted *(built 2026-09-18, for veto)*.
