# Releasing the Tingra apps

*Tingra Cameras has its own plan, at the end of this document ("Releasing Tingra Cameras"), which reuses this one. Everything before it concerns Tingra.app.*

*Plan of 2026-10-13. **All eleven decisions were approved by Larry on 2026-10-13.** The two pieces that wait on nothing were built the same day ("Built so far", below); the spike (Phase 0) comes next and may amend the decisions, as PLUGINS.md's did. `tingra-cli`'s release stays specified in CLI.md, "Distribution"; this document covers the app and what changes around the CLI when the app ships.*

## Why now

Everything since roadmap step 6 lives in `apps/tingra-app`, and nobody can install it. The CLI has a release path (`scripts/release-cli.sh`, `release-cli.yml`, the tap's formula) and so do the kits (`release-sdk.sh`); the app has `scripts/run-app.sh`, which is a developer's loop. Three open items already wait on an installable app:

- **The plug-in gallery** (PLUGINS.md, Phase 5) lists "Tingra.app shipping (the cask)" as a prerequisite.
- **The daemon's name in Login Items** (TODO.md, "Release mechanics") is fixed by associating the daemon with the app bundle.
- **The daemon's secure storage** (DESTINATIONS.md, "The decision, in two halves", half (b)) needs the daemon to ship as its own bundle inside `Tingra.app`.

## What is already decided

These stand, and this plan builds on them rather than reopening them:

- **`Tingra.app` bundles the CLI; one Homebrew cask; the `tingra-cli` formula stays as the headless path** (decided 2026-07-11; DONE.md).
- **A bare helper in `Contents/MacOS` is not an option.** A provisioning profile belongs to a bundle's main executable, so a helper beside it is SIGKILLed at `exec` exactly as `tingra-cli` v0.1.1 was. The daemon joins the keychain group only as its own bundle with its own profile (DESTINATIONS.md, "What the probe measured").
- **Identifiers live under `com.moonwink.tingra.*`**, the app is `com.moonwink.tingra.app`, and nothing personal to one developer is committed (CLAUDE.md, "Signing").
- **Apple Silicon only, macOS 15.0+, Developer ID signed with the hardened runtime, notarized, not sandboxed.**

## What makes the app harder than the CLI

The CLI release signs one bare Mach-O and two frameworks with `codesign`. The app differs in four ways, and each one shapes a decision below:

1. **It carries a restricted entitlement.** `keychain-access-groups` is authorized by a provisioning profile embedded in the bundle. Today that is a development profile Xcode's automatic signing fetches. A Developer ID build needs a **Developer ID provisioning profile**, which only the account holder can create, and a signature that profile does not cover is killed at `exec` with no error, no log line, and no crash report (`scripts/sign-app.sh`'s header).
2. **The entitlement contains a build variable.** `$(AppIdentifierPrefix)` expands at signing, in Xcode. `codesign` does not expand it, and embedding it literally is what made v0.1.1 unrunnable.
3. **It nests signed code.** `TingraNotes.appex` (sandboxed, its own entitlements), `TingraPlugInKit.framework`, and `TingraEventBus.framework` each need the release identity, inside out.
4. **No signature inspection catches a kill at `exec`.** v0.1.1 passed `codesign --verify`, the entitlements dump, and notarization. Only running the binary caught it.

## The decisions

**1. Two slices: the app alone first, the CLI and daemon inside it second.** Slice 1 ships `Tingra.app` signed, notarized, in a disk image, with a cask. Slice 2 builds the daemon as its own bundle inside the app, puts `tingra-cli` on the `PATH` from the cask, and closes the Login Items and daemon-keychain items. *Why split:* slice 1 already has unknowns no session has measured (the Developer ID profile, a fresh install's extension enablement), and slice 2 changes the LaunchAgent and the relationship between the cask and the formula. Until slice 2, an operator who wants both installs the cask and the formula, which is today's state plus an app.

**2. Xcode does the signing: `xcodebuild archive`, then `xcodebuild -exportArchive` with the `developer-id` method and manual signing.** The script never hand-signs the app bundle with `codesign`. Export re-signs every nested bundle in order, expands the entitlements' build variables, embeds the profile, and takes a per-bundle-identifier profile map, so the app gets its profile and Notes gets none. The export options property list is **generated by the script at run time** from the environment, because it names the team. *Rejected:* manual-signing overrides on the `xcodebuild` command line (a command-line setting applies to every target, so Notes and the kits would be handed the app's profile); and a hand-rolled inside-out `codesign` pass (difficulties 1–3 above are exactly what it gets wrong).

**3. A Developer ID provisioning profile, kept as a secret, never committed.** Larry creates it once in the developer portal. Locally `TINGRA_APP_PROFILE` names the `.provisionprofile` file; in CI the secret of the same name holds its base64, written into the runner's profile folder beside the throwaway keychain `release-cli.yml` already builds. The team identifier is read from `TINGRA_SIGN_ID`'s suffix, so no new variable carries it. Whether the profile is issued against the existing wildcard App ID or a new explicit `com.moonwink.tingra.app` is spike row A: it decides the keychain group's prefix, and on this account those differ (DESTINATIONS.md, "The decision, in two halves": this account carries a legacy App ID prefix distinct from its team identifier).

**4. The artifact is one disk image, `Tingra-<version>-arm64.dmg`.** Built with `hdiutil` alone: the app and an `/Applications` symlink, no background art, no third-party tool. The app is notarized and stapled first, then the image is signed, notarized, and stapled, so the app still opens offline after it is dragged out. Two notarization submissions per release is the cost. *Rejected:* a zip (works for the cask, but a direct download gets no drag-to-Applications affordance and browsers unpack it into `~/Downloads`, where the app then runs translocated); a `.pkg` (an app that installs by drag has no need for an installer, and it would need the Installer identity).

**5. The cask is `tingra`, in the existing tap.** `brew install --cask larryaasen/tingra/tingra`. The template lives at `packaging/homebrew/tingra.rb` and is rendered into `larryaasen/homebrew-tingra` as `Casks/tingra.rb` by the publish step, as the formula is. It declares `depends_on arch: :arm64`, `depends_on macos: ">= :sequoia"`, `app "Tingra.app"`, and a `zap` stanza naming `~/Library/Application Support/Tingra`, the log folder, and the preferences file. `zap` does not touch the Keychain, and the cask's caveats say so.

**6. One product version, one tag, one GitHub release.** The app takes the product's `v<MAJOR>.<MINOR>.<PATCH>` number, the one `tingra-cli version` prints, and the first release with an app is **0.2.0**. One release carries the CLI's zip and `.pkg` and the app's disk image. The app target's `MARKETING_VERSION` (now a literal `1.0` in the project file) moves to a `TINGRA_VERSION` line in `Tingra.xcconfig` that the release script bumps with `TingraCLIVersion.current`; `CFBundleVersion` is the same three integers. *Why one:* slice 2 puts the CLI inside the app, and two numbers for one bundle would need a compatibility story. *The cost:* an app notarization that stalls holds the CLI's release too; the scripts are already resumable, which is the mitigation. *Rejected:* an `app-v<x.y.z>` tag series.

**7. The scripts and the workflow are renamed for what they now do.** `release-cli.sh` → `release.sh`, `release-cli-publish.sh` → `release-publish.sh`, `release-cli.yml` → `release.yml`. `release-cli-package.sh` keeps its name and its job, and a new `release-app-package.sh` sits beside it (archive → export → verify → run → notarize → staple → disk image → sha256). Without credentials it stages an unsigned development build in `dist/tingra-app/`, as its sibling does.

**8. The release runs the app before notarizing it.** `Tingra.app/Contents/MacOS/Tingra --version` prints the version and exits 0, handled in the `@main` entry before any scene or the engine exists. This is the one new piece of app code in slice 1, and it is the only check that catches a signature the kernel refuses. Around it, the script asserts:
   - `codesign --verify --deep --strict` passes and the authority is `Developer ID Application`;
   - the app's entitlements carry a keychain group with **no literal `$(`** in it, and `Contents/embedded.provisionprofile` exists;
   - `TingraNotes.appex` is sandboxed and signed by the same team;
   - both kit frameworks are present, arm64 only, and carry no `__llvm_prf_cnts` section;
   - `FixturePlugIn.tingraplugin` is not in the bundle;
   - after stapling, `spctl --assess` accepts the app and the image.

**9. No updater in the first release.** The cask is the update path (`brew upgrade --cask tingra`); a direct download is replaced by hand. An updater is a later decision of its own. The likely answer is Sparkle behind an app-only seam, under design principle 4 (adopt the thankless parts), since a self-replacing signed app is security work Tingra should not write. It is not decided here, and nothing in slice 1 forecloses it: Sparkle consumes the same signed disk image.

**10. The deployment floor stays at macOS 15.0.** CLAUDE.md, "Platform Support" says to revisit the app's floor when phase 3 begins. The app builds and runs there today, so nothing argues for raising it.

**11. The logo is not a gate.** TODO.md, "Tingra needs a logo" stays open. A 0.x release ships with whatever `AppIcon` holds; the disk image has no artwork to redo when the mark arrives.

### Spike findings

**Row A, 2026-10-13: an explicit App ID with the legacy prefix.** Larry issued the profile, named "Tingra Developer ID", against a new explicit App ID `com.moonwink.tingra.app` registered under the account's legacy App ID prefix, not the Team ID. Read from the downloaded file:

- A Developer ID profile: macOS, `ProvisionsAllDevices` true, expiring 2044.
- It grants `keychain-access-groups` `<prefix>.*`, with the **same prefix as the development build's** wildcard profile. A release build and a development build therefore share `<prefix>.com.moonwink.tingra.shared`, and a key filed by one is visible to the other. Decision 3's open question is closed with nothing to amend.
- It names one certificate, the Developer ID Application identity already in Larry's keychain and in `TINGRA_CERT_P12`.

**The certificate expires on 2027-02-01, and the profile goes with it.** A profile names the certificate it was issued for, so the 2044 date is not the one that matters: on renewing the Developer ID Application certificate, regenerate this profile against the new one and replace the `TINGRA_APP_PROFILE` secret in the same sitting. Apps already signed and timestamped keep running past the expiry; only new signing stops. `packaging/README.md`'s rotation recipe gains this step when the secret is added.

**Row B, first half, 2026-10-13: the Release configuration did not link, and now does.** The first `xcodebuild archive` stopped at the linker with libsrt's symbols undefined *for x86_64*. An archive builds for a generic Mac destination, so a Release build without an explicit architecture is universal, and the prebuilt libsrt HaishinKit's SRT output carries is arm64 only. Nothing had built that way before: every development and test build names `arch=arm64` in its destination. `ARCHS = arm64` in `Tingra.xcconfig` makes the project say what CLAUDE.md already required, for every target and configuration. With it, both archives build:

- **Development-signed** (automatic signing, `Local.xcconfig` present): arm64 only, the hardened runtime, the keychain group in its entitlements, a development profile embedded, Notes in `Contents/Extensions`, both kit frameworks, no fixture, no coverage section, and `--version` prints `0.1.4-dev`.
- **Unsigned** (`CODE_SIGNING_ALLOWED=NO`, the CI shape): the same contents, but the linker's ad-hoc signature carries **no entitlements**. Whether the export restores them from the project or ships without them is the second half of row B.
- **Archiving warned that `TingraNotes.appex` "must be embedded in the parent app bundle's Extensions directory"**, naming a path under `BuildProductsPath`. Fixed 2026-10-14: the app target's Embed ExtensionKit Extensions phase copied into the *products directory* (`dstSubfolderSpec = 16`) at `$(EXTENSIONS_FOLDER_PATH)`. In an ordinary build that is the app being built; an archive builds the app in `InstallationBuildProductsLocation` and leaves the products directory at `BuildProductsPath/Release`, so the copy aimed at a different `Tingra.app` than the one archived. The phase now copies into the app bundle itself (`dstSubfolderSpec = 1`, `dstPath = Contents/Extensions`), which follows the app wherever it is built. The Debug build embeds Notes as before, the Developer ID archive no longer warns, and its app holds Notes (still sandboxed) and the extension point. The earlier archives held Notes too, which says Xcode was placing it a second way; the phase no longer depends on that.

**Row B, second half, 2026-10-14: export works, and CI must archive with the Developer ID identity.** With the profile installed (a double-click on macOS hands a `.provisionprofile` to System Settings, not to Xcode; it has to be copied into `~/Library/Developer/Xcode/UserData/Provisioning Profiles/`, which the release script will do itself), `xcodebuild -exportArchive` with the `developer-id` method succeeds from every archive, and what it produces depends entirely on what the archive recorded:

- **From the development-signed archive:** correct. Developer ID authority, the hardened runtime, a secure timestamp, `<prefix>.com.moonwink.tingra.shared` expanded, camera and audio-input, the Developer ID profile embedded, Notes sandboxed, both kits Developer ID signed, `--version` exit 0.
- **From the unsigned archive:** it verifies, and it is **unusable** — no hardened runtime, no entitlements at all, Notes unsandboxed. Export re-signs with what the archive recorded, and an unsigned archive recorded nothing. Decision 2's "CI archives with an ad-hoc identity instead" does not work either: with no team, the build refuses to archive ("requires a provisioning profile"), because the keychain entitlement needs one at build time.
- **So the archive itself signs with Developer ID**: `CODE_SIGN_STYLE=Manual`, `CODE_SIGN_IDENTITY="Developer ID Application"`, the team from `TINGRA_SIGN_ID`, and the profile's name. Passing that name as `PROVISIONING_PROFILE_SPECIFIER` on the command line fails, as Decision 2 predicted — Notes and both kit frameworks reject a profile issued for another bundle — so the app target's `PROVISIONING_PROFILE_SPECIFIER` now reads `$(TINGRA_APP_PROFILE_SPECIFIER)`, empty in `Tingra.xcconfig` (development builds keep automatic signing) and set by the release. That archive, exported, matches the development-signed one in every check above. Export stays in the pipeline: it is what applies the `developer-id` method's checks and lays the app out for notarization.

**Row C, first half, 2026-10-14: the Developer ID app launches and boots the engine.** Opened through LaunchServices from the scratchpad with `TINGRA_CONSOLE_LOG=1`, it ran past `exec` (no SIGKILL), reported `app.launched` at `0.1.4-dev`, discovered every camera, microphone, and display, and activated all six first-party host plug-ins. Whether it reads a stream key filed by a development build is still open: keys are read only when the Streaming settings pane shows a destination, and that needs the window.

**Row C, second half, 2026-10-14: the Developer ID app reads a key a development build filed.** Larry opened Settings → Streaming in the release build and the saved destination's key field was filled; the full log (written on quit) holds no `securestore` event of any kind. The shared group behaves exactly as row A predicted: one legacy prefix, one `<prefix>.com.moonwink.tingra.shared`, both signatures inside it. The log's only errors were Screen Recording refusals for the two displays, which the TCC row below explains. Notes was discovered and enabled, but on a Mac where it had been approved before, so that says nothing about row E. The scratch copy's extension registration was removed afterwards with `pluginkit -r`, leaving the development build's.

**Row C passes.** Writing a key was not exercised; it goes through the same entitlement and the same group as the read, which is the half that fails with −34018 when the entitlement is wrong.

**Row F, early, 2026-10-14: TCC treats the release build as a different app.** The same launch logged `authorization.status camera=notDetermined microphone=notDetermined screenRecording=denied`, on a Mac where the development build holds all three grants. TCC keys a grant to the bundle identifier *and* its designated requirement, and a Developer ID signature's requirement differs from an Apple Development one's. Answering the release build's prompt either way replaces the development build's record, so alternating the two on one Mac flips the grants back and forth. Larry accepted the Camera and Microphone prompts during row C, which moved those two grants to the release build; the development build asks again on its next run. **Decided by Larry, 2026-10-14: development builds keep sharing `com.moonwink.tingra.app`.** The cost is known and accepted: alternating a release build and a development build on one Mac moves the Camera, Microphone, and Screen Recording grants to whichever answered last, and the other asks again. What sharing keeps is one keychain group, one extension point identifier, and one Application Support folder, so a development build sees the operator's real keys, destinations, and project. Row F is closed.

**Row D, 2026-10-14: both notarizations pass, both staples validate, and a quarantined download assesses as notarized.** The app exported from the Developer ID archive (the CI shape) was zipped with `ditto -c -k --keepParent` and submitted with `notarytool --keychain-profile TINGRA_NOTARY --wait`: **Accepted** in about a minute, with no issues in the notary log. Stapled; `stapler validate` passes; `spctl --assess --type execute` reads `source=Notarized Developer ID`. The disk image — `hdiutil create -format UDZO` over the stapled app and an `/Applications` symlink, 4.7 MB — was signed with the Developer ID identity and `--timestamp`, submitted on its own, **Accepted**, stapled, and assessed `accepted` under `--type open --context context:primary-signature`. A copy marked with the `com.apple.quarantine` attribute a browser download carries, mounted with `hdiutil attach -nobrowse`, held an app whose staple validates, that `spctl` accepts as notarized, that `syspolicy_check distribution` passes ("ready for distribution"), and whose `--version` exits 0. Decision 4's two submissions cost about two minutes per release.

What row D cannot show is the first launch of a quarantined app by a person, with Gatekeeper's dialog and the TCC prompts; that is row E, on a clean account. Mounting and stapling registered two more copies with Launch Services (the stapled app and the one on the image), without their Notes; both were unregistered, which the script's cleanup has to cover too.

**A side effect on the development Mac, 2026-10-14: archiving broke Notes in the Xcode build.** `xcodebuild archive` leaves a Developer ID copy of the app in DerivedData (`ArchiveIntermediates/…/InstallationBuildProductsLocation/Applications/Tingra.app`), and Launch Services registers it and its Notes. That Notes carried the same identifier and version as the Debug build's. Larry's next Xcode run discovered Notes but never started it, with the pane stuck on "Loading plug-in…" and `plugin.availability` reporting one unapproved extension where it had reported none. Unregistering the staging copy and the exported app (`pluginkit -r` on the appex, `lsregister -u` on each app) left only the Debug build registered. The running instance reported `unapproved=0` seconds after the unregister, and Larry's relaunch started Notes, so the extra copy was the cause, not the version string changing from `1.0` to `0.1.4-dev`. The system picks one copy per identifier, and with two at the same version it picked the unapproved one. **`release-app-package.sh` unregisters every copy it builds before it exits**, so a release cut on a development Mac leaves that Mac as it found it. The archive step's Notes warning, fixed separately (row B above), was a different defect: it concerned where the copy phase wrote, not what Launch Services registered.

## Built so far

# Releasing Tingra Cameras

*Plan of 2026-10-31. **All fifteen decisions were approved by Larry on 2026-10-31.** Nothing here is built yet, and the spike may amend them, as it did Tingra.app's. The spike findings above were measured on Tingra.app and are cited rather than repeated; the Phase 0 below covers only what differs.*

## Why it goes first

Tingra Cameras is the easier app to ship. It carries no restricted entitlement (only `device.camera` and `disable-library-validation`), so it needs no provisioning profile, and that profile was difficulty 1 and 2 of Tingra.app's list. It embeds no extension, so difficulty 3 shrinks to the two kit frameworks, and archiving cannot break a Notes extension the way it did for Tingra.app ("A side effect on the development Mac", above). It has no daemon and no relationship with the CLI. Building its release first produces the packaging script Tingra.app then reuses, and it tests the disk image and cask path with real users on a smaller app.

## What an archive does today

Measured 2026-10-31: `xcodebuild archive` with `CODE_SIGNING_ALLOWED=NO`, into the scratchpad, then run once and deleted.

- **The archived app does not launch.** It stops in `dyld` with `Library not loaded: @rpath/TingraEventBus.framework/Versions/A/TingraEventBus`, because `Contents/Frameworks` does not exist. The kits are dynamic products (PLUGINS.md, Decision 22), and this project has no Embed Frameworks phase, while Tingra.app's project does. **A Debug build hides this:** its rpath includes `Build/Products/Debug/PackageFrameworks` in DerivedData, so the app runs on the Mac that built it and would fail on every other Mac.
- **It is universal** (`x86_64 arm64`), because the project sets no `ARCHS`. Row B found the same gap in Tingra.app.
- **Its identity is unfinished:** `com.moonwink.tingra-cameras`, version `1.0`, build `1`, minimum system `26.5`.
- **It has no icon.** `AppIcon.appiconset` holds only `Contents.json`.
- **Archiving warns** that no App Category is set.
- **CI never builds it.** `format-test.yml` builds `apps/tingra-cli` and `apps/tingra-app` but not this app, though CLAUDE.md says every app gets a warning-clean build. The project also has no test target, so the test command in its `CLAUDE.md` has nothing to run.

## The decisions

**C1. It ships on its own, ahead of Tingra.app's slice 1.** Neither release waits on the other.

**C2. Its own version and tags.** `cameras-v<x.y.z>` tags and their own GitHub releases, first version **0.1.0**, with a `TINGRA_CAMERAS_VERSION` line in this app's `Tingra.xcconfig` read for both `CFBundleShortVersionString` and `CFBundleVersion`. Decision 6's single number exists because the CLI will live inside Tingra.app; this app is standalone and links no CLI. Its releases are published with `--latest=false`, so the repository's latest release stays the engine's. *Rejected:* joining the product version, which would make a Cameras fix wait for, or force, an engine release.

**C3. The bundle identifier becomes `com.moonwink.tingra.cameras`,** following the `com.moonwink.tingra.*` rule. This is the last cheap moment: after a release, the change would reset every user's camera permission and preferences. On the development Mac it costs one new camera prompt and the `UserDefaults` values (remembered camera, appearance, sidebar state). Presets are unaffected, since `camera-presets.json` lives by path.

**C4. The target embeds both kit frameworks,** with an Embed Frameworks phase and code-sign-on-copy, as Tingra.app's target does. This is the blocker above.

**C5. `ARCHS = arm64` in this app's `Tingra.xcconfig`,** as in Tingra.app's, and an `LSApplicationCategoryType` of `public.app-category.video` to clear the archive warning.

**C6. The floor is macOS 26.0, not 26.5.** `.glassEffect` sets the floor at 26, which this app's `CLAUDE.md` already states. Nothing found in the code asks for 26.5, and the compiler will name anything that does. Unlike Tingra.app (Decision 10), this app keeps a higher floor than the engine's macOS 15.

**C7. Xcode signs, as row B established:** archive with manual signing and the Developer ID Application identity, then export with the `developer-id` method. An unsigned archive records no entitlements, so export would ship an app without camera access. There is no profile, so no `PROVISIONING_PROFILE_SPECIFIER` and no new secret. The Developer ID certificate's 2027-02-01 expiry applies, but with nothing to regenerate.

**C8. One disk image, `Tingra-Cameras-<version>-arm64.dmg`,** built and notarized as Decision 4 describes: app stapled first, then the image signed, notarized, and stapled.

**C9. A `tingra-cameras` cask in the existing tap,** rendered from `packaging/homebrew/tingra-cameras.rb`: `depends_on arch: :arm64`, `depends_on macos: ">= :tahoe"`, `app "Tingra Cameras.app"`. **Its `zap` names files, never a folder:** `camera-presets.json`, the preferences file, and saved application state. `~/Library/Application Support/Tingra` is shared with Tingra.app and holds its destinations and plug-in settings, so zapping this cask must not remove that folder.

**C10. One packaging script for both apps.** `scripts/release-app-package.sh --app cameras|tingra` holds the shared pipeline from Decision 7 (archive → export → verify → run → notarize → staple → disk image → sha256, and the unregistering of every copy it builds), with a per-app table of project, scheme, product name, and checks. Only Cameras is wired up at first. `scripts/release-cameras.sh` and a manually dispatched `release-cameras.yml` wrap it, gated on `format-test.yml`, and tag, publish, and render the cask. They use the secrets `release-cli.yml` already uses. The product name has a space, so the script quotes every path.

**C11. The release runs the app before notarizing it,** as Decision 8 does. `Tingra Cameras --version` prints the version and exits 0 before any scene or the engine exists, so `TingraCamerasApp` stops being the `@main` entry, as `TingraApp` did. `LaunchArguments` moves from Tingra.app into `TingraHost`, so both apps share one rule; TYPES.md gains the type in that change. This check alone would have caught the missing frameworks. Around it, the script asserts: `codesign --verify --deep --strict` with the `Developer ID Application` authority; exactly the two expected entitlements and no `get-task-allow`; both kit frameworks present and signed; arm64 only; no `__llvm_prf_cnts` section; an icon in the bundle; and `spctl --assess` accepting the app and the image after stapling.

**C12. CI builds it.** `format-test.yml` gains a warning-clean, unsigned build of this app, so the build stops relying on someone opening Xcode. A test target is not a release gate: the logic worth testing (presets, parameters) lives in `TingraHost` and is tested there.

**C13. The icon is a gate here.** This overrides Decision 11 for this app. Tingra.app can wait for the logo because its first users are installing an engine; a small utility with the blank generic icon looks broken in the Dock and Applications. Larry supplies the art, and it need not wait for the Tingra logo.

**C14. No updater in the first release,** as Decision 9. `brew upgrade --cask tingra-cameras`, or replace the app by hand.

**C15. Development and release builds share the identifier,** with the same accepted cost as row F: alternating them moves the camera grant to whichever answered last.

## Built so far

**C3–C6, 2026-10-31.** The target is `com.moonwink.tingra.cameras`, embeds both kit frameworks, is categorized as video, and has a floor of macOS 26.0. `Tingra.xcconfig` holds `ARCHS = arm64` and `TINGRA_CAMERAS_VERSION = 0.1.0-dev`, which both version keys read. The app built at the new floor with no code change, and an archive now launches and stays running instead of stopping in `dyld`.

**`ARCHS` in the xcconfig does not reach the kits (amends C5).** A project's xcconfig applies to its own targets, not to Swift package targets, so the archive's app was arm64 while both kit frameworks stayed `x86_64 arm64`. Passing `ARCHS=arm64` on the `xcodebuild archive` command line makes all three arm64, so **the packaging script must pass it**, keeping the xcconfig line for ordinary builds. Decision 8 asserts the same for Tingra.app and has the same exposure: row B's "arm64 only" may have read only the app's binary. Check the kits there too.

**The Team ID came out of the project file.** Both project-level configurations carried a literal `DEVELOPMENT_TEAM`, which CLAUDE.md forbids and which overrode the xcconfig's `$(TINGRA_DEVELOPMENT_TEAM)`. The commit that last re-added it is 82b9582, so it is in the public history. Xcode re-adds this line when a team is picked in the Signing tab, so watch for it in diffs.

**C13, 2026-11-01.** Both apps' `AppIcon` sets now hold their icon, every size scaled from the masters in `docs/logos`. The masters are opaque, full-bleed squares, and macOS 26 masked both when asked for the built bundles' icons. **macOS 15 is unchecked:** Tingra.app's floor is lower than the system that adds the mask, so its icon may show as a hard-edged square there. Check on a macOS 15 install before Tingra.app ships. Tingra Cameras needs macOS 26, so it is not exposed.

**C11, 2026-11-03.** `Tingra Cameras --version` prints `0.1.0-dev` and exits 0, with nothing on standard error; `TingraCamerasMain` is the `@main` entry and `TingraCamerasApp` is not, as Decision 8 did for Tingra.app. `LaunchArguments` moved into `TingraHost`, and **`AppVersion` moved with it**: `versionLine(for:)` takes one, and the two apps carried identical copies. Their tests moved too, with two new ones (a path holding a space, and reading both keys from a bundle on disk). The app keeps the two tests only its own bundle can run. `Tingra --version` still prints `0.1.4-dev`, exit 0. The release script's assertions around this check belong to C10.

**C10's packaging script, 2026-11-06.** `scripts/release-app-package.sh --app cameras [version]` runs the pipeline from archive to sha256 with the spike's recipes. Its per-app table holds Cameras alone; `--app tingra` refuses and names what Tingra.app still needs. Without `TINGRA_SIGN_ID` it archives with `CODE_SIGNING_ALLOWED=NO` and skips the export, the signature checks, and notarization. It verifies, runs, and images the unsigned app, and warns that the result must not be published. With it, the team is read from the identity's suffix, and the export options list is generated into the app's git-ignored `.build/xcodebuild`, so no tracked file names the signer. It writes only `dist/tingra-cameras/`, leaving the rest of `dist/` alone. Run on Larry's Mac both ways: unsigned, then signed and notarized, where every check passed, both submissions were Accepted, and the app inside the mounted image ran. No copy was left registered, even a minute after exit. Three things the runs found, each now in the script:

- **The staged app must never be run.** Once a bundle whose code the notary service has already accepted has run, the system protects it with a `com.apple.macl` attribute, and the stapler can no longer write the ticket into it: error 73, "Could not remove existing ticket". A release's code is new at run time, so the first signed run stapled. A rerun that rebuilt identical code did not. `--version` therefore runs on a `ditto` copy, which is byte for byte the staged app, and the copy is deleted afterwards.
- **The staged app is copied out of the export, never moved.** The exported bundle carries the same attribute, which `ditto` does not copy.
- **Unregistering is not enough for a copy left on disk.** After one notarized run, Launch Services re-registered the export's copy *after* the exit trap had unregistered it. The export is now deleted once the app is copied out of it. The trap still unregisters every copy under the build folder and `dist/tingra-cameras/`, asking Launch Services which ones it holds rather than guessing paths.

**A Team ID came back into the project file during row E.** Larry's Xcode re-added `DEVELOPMENT_TEAM` to both project-level configurations at 08:18 on 2026-11-06, seven minutes before the script first ran, with nothing else changed. It was reverted, since `Local.xcconfig` holds the value. This is the hazard the paragraph above names: watch every diff of this project file.

### Spike findings

**Row A, 2026-11-05: the exported app is what C4, C7, and C11 describe, and it launches.** Archived with the shape C7 names: `xcodebuild archive` for `generic/platform=macOS`, with `ARCHS=arm64 CODE_SIGN_STYLE=Manual CODE_SIGN_IDENTITY="Developer ID Application"` and `DEVELOPMENT_TEAM` read from the Developer ID identity in the keychain, all on the command line, and no profile. The archive built with no warnings. It was exported with `-exportArchive` and a generated options list: `method` `developer-id`, `signingStyle` `manual`, the same certificate and team. Both steps succeeded on the first try, and the app holds:

- the `Developer ID Application` authority, the hardened runtime (`flags=0x10000(runtime)`), and a secure timestamp. `codesign --verify --deep --strict` passes, and the app satisfies its designated requirement;
- **exactly** `device.camera` and `cs.disable-library-validation`, with no `get-task-allow` and no `embedded.provisionprofile`;
- `TingraEventBus.framework` and `TingraPlugInKit.framework` in `Contents/Frameworks`, each signed with Developer ID, with the runtime flag and a timestamp, and each verifying on its own. The binary links both through `@rpath`, and its one rpath is `@executable_path/../Frameworks`;
- **arm64 only in all three binaries.** C5's amendment holds: `ARCHS=arm64` on the command line reaches the package frameworks;
- no `__llvm_prf_cnts` section in any of the three;
- `AppIcon.icns` and `Assets.car`, with `com.moonwink.tingra.cameras`, `0.1.0-dev` in both version keys, a floor of 26.0, and the video category.

`Tingra Cameras --version` prints `0.1.0-dev` and exits 0. The GUI binary ran for six seconds and was still running when it was terminated. Nothing in row A contradicts a decision.

**Row C, 2026-11-05: both notarizations pass and both staples validate.** The app was zipped with `ditto -c -k --keepParent` and submitted with `notarytool --keychain-profile TINGRA_NOTARY --wait`. It was **Accepted** in about 25 seconds, and the notary log lists no issues. After stapling, `stapler validate` passes and `spctl --assess --type execute` reads `source=Notarized Developer ID`. The disk image was made with `hdiutil create -format UDZO -fs HFS+` over the stapled app and an `/Applications` symlink, volume name "Tingra Cameras", and came to 1.7 MB. It was signed with the Developer ID identity and `--timestamp`, submitted on its own, **Accepted** in about 25 seconds, and stapled. It is `accepted` under `--type open --context context:primary-signature`. A copy carrying the `com.apple.quarantine` attribute a browser writes was mounted with `hdiutil attach -nobrowse -readonly`. Its app's staple validates, `spctl` accepts it as notarized, `syspolicy_check distribution` passes, and `--version` exits 0. C8 stands as written.

**For row D, a second build whose code differs.** A re-export of the same archive would carry the same code directory hash, so a surviving grant would prove nothing. A second archive was therefore built with `TINGRA_CAMERAS_VERSION=0.1.1-dev` on the command line, leaving the tracked xcconfig untouched, then exported, notarized, stapled, and imaged the same way (both submissions Accepted). Its code directory hash differs from the first build's. Its designated requirement is identical: the identifier plus the Developer ID leaf certificate's team. That requirement is what TCC keys a grant to, so the grant should survive the replacement, and row D checks that it does.

**Row B, 2026-11-05: the Developer ID build streams both cameras and drives the Razer's controls, so no entitlement is missing.** Larry ran row A's export through `open`, not from Terminal, so TCC asked on behalf of the app and not the terminal. He checked the FaceTime HD Camera and the Razer Kiyo Pro and reports every item a pass: preview, a slider, an Auto switch, and a preset recall. The event log he captured shows the Razer half:

- discovery of all four cameras;
- the Razer's 16 controls read through `TingraUVC`;
- the default preset applied at launch;
- `input.started` and `preview.firstFrame`;
- Brightness slider moves and a reset;
- `whiteBalanceAuto` flipped on and off.

The log file stops before the FaceTime HD Camera was selected, so that half rests on Larry's report. Standard output to a file is block-buffered, and its tail was not written out. Two things the log shows that were not asked:

- **The camera prompt was new.** The release build logged `camera=notDetermined` on a Mac where the Debug build holds the grant: row F's TCC result, as C15 expects. The `authorization.changed … to=granted` event comes about 20 seconds after the first frame, because the permission is re-read on app activation, not when the prompt is answered.
- **The preset reached the Razer before the camera grant existed.** Control access goes through IOUSBHost, which TCC does not gate, so `cameraPreset.applied` precedes `authorization.status`. That is how USB control transfers work, not a release defect. It does mean a denied camera permission leaves the controls writable.

Row B contradicts no decision.

**Row D, 2026-11-05: a fresh install works.** Larry ran it on a clean user account on a second Mac, following the row's checklist: both disk images quarantined as a browser download is, then installed `0.1.0-dev` from its image into `/Applications`. Then he replaced it with `0.1.1-dev`, the build whose code hash differs. He reports every check a pass:

- the app opened with only Gatekeeper's standard first-launch dialog, and no System Settings override;
- the camera prompt named "Tingra Cameras";
- the grant survived the replacement with no second prompt, and the preview went live.

TCC therefore keys this app's grant to its designated requirement, not its code hash, as row C's comparison predicted. A release that replaces the app keeps the user's camera permission. Row D contradicts no decision.

**Row E, 2026-11-06: the release build and Tingra.app's Debug build leave each other alone.** Row D's second build was copied into `/Applications` on the development Mac with `ditto`. Larry then ran it on the same camera as a running Tingra.app Debug build and reports every step a pass:

- Tingra's camera input kept streaming while Cameras opened the camera, and a Razer control changed in Cameras showed in Tingra's picture, as one piece of hardware should;
- after quitting both and relaunching, Tingra.app's destinations, project, and plug-in settings were intact, and so were Cameras' presets.

Checksums of `~/Library/Application Support/Tingra` taken before row E match the ones taken after, file for file. The one exception is `log-session-id`, which Tingra.app advances on every launch. Sharing the folder is safe: each app writes only its own files, and C9's `zap` rule (files, never the folder) stands. Row E's checklist asked for a new preset to be saved, and Larry saved none, which is why `camera-presets.json` is unchanged since 2026-10-29. So the release build read the presets but never wrote one. Writing is a plain file write through `CameraPresetStore`, the same code a Debug build runs, and it needs no entitlement, so nothing about the release signature bears on it.

**Launch Services, as for Tingra.app.** The archive registers its staging copy (`ArchiveIntermediates/…/InstallationBuildProductsLocation/Applications/Tingra Cameras.app`), and mounting the image registers the copy on the volume. Earlier sessions' scratch builds had left seven more registrations behind. This app embeds no extension, so the stray copies broke nothing, but they do crowd Open With and Launch Services' choice of copy. All of them were unregistered with `lsregister -u`, leaving only the Xcode Debug build and the copy row B runs. C10's rule to unregister every copy it builds applies to this app unchanged.
